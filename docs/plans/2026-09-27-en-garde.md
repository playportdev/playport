# Plan: En Garde! to its first frame

**Date:** 2026-09-27. **Kind:** plan. **Done** 2026-09-30: the game plays
([evidence](../evidence/2026-09-30-en-garde.md)); the steps below were not needed.
**Title:** En Garde! (Steam app 1654660), Unreal Engine, Direct3D 11 and 12,
installed from Steam into `C:\Games\EnGarde`.

## Where it stands

Three things kept it from starting. Two are fixed on the `steam-for-games`
branch ([the Steam plan](2026-09-27-steam-for-games.md), phases 1 and 2):

1. **The bootstrap.** `EnGarde.exe` is Unreal's launcher, which only starts
   `EnGarde\Binaries\Win64\EnGarde-Win64-Shipping.exe` as a second process.
   The one-process runtime never started that process, and the launcher waited
   on a black screen. Adoption now picks the shipping executable itself.
2. **SteamStub 3.1 x64** on the shipping executable. The DRM made it exit
   `0x35` with no Steam running. It is now removed at launch: the original
   entry point `0x51c12a0` is restored, `.bind` is dropped, and the game's
   copy is kept as `.orig`. The emulator is in place of its `steam_api64.dll`.
3. **Open: a fault in FEX.** About 20 s after start (IPA `d8a19426…`, run
   `20260927T232050`), the game faults on a null read in ARM64EC code at
   `pc 0x120eb6644`: guest `0x71fe809644`, `ldr x8, [x0]` with `x0 = 0`. The
   code is inside the first ARM64EC module the loader maps before kernel32
   (a 0x3fb000-byte image at `0x71fe6f0000`, which should be `xtajit64.dll`).
   The fault is re-delivered 2000 times until the runtime ends the process.
   Unreal had not created `Saved\` yet, so it never wrote its log: the fault
   is early in engine start.

## Steps, in order

Each step is a `pp ui --play app-1654660 --wait 300` on the branch's IPA,
unless it says otherwise.

1. **Rule the unwrap in or out.**
   - Unwrap keeping `.bind` in place (entry point and CheckSum only; a test-only
     switch in `SteamStub.unwrap`, not a setting).
   - If the fault moves or goes away, the dropped section or the rewritten
     `SizeOfImage` is to blame, so compare with what the loader and FEX read
     from the headers.
   - Then check the stub's other effects on 3.1: TLS callbacks, and imports
     or relocations the stub resolved itself (flags `0x6`).
2. **Name the module and the function.**
   - Confirm the module at `0x71fe6f0000` from the loader's `Load module`
     lines.
   - Symbolise `0x71fe809644 - 0x71fe6f0000 = 0x119644` against this build's
     `libarm64ecfex.dll` (`llvm-objdump -d` with its PDB-less symbols, or the
     map from `build/stages/fex.sh`).
   - Record the x64 guest RIP and the thunk that entered EC code: the
     `[rtcs]` and `[guest-rip]` lines hold the EC side only.
3. **What the game was doing.**
   - Start it with `-log` and `-stdout` (the game page's launch arguments)
     so Unreal writes to the console before `Saved\` exists.
   - Set `WINEDEBUG=+loaddll,+seh` for one run.
   - The last DLL loaded and the last Win32 call before the fault narrow it
     to a subsystem: a 124 MB executable's CRT start, `D3D12`, Oodle,
     OpenImageDenoise or TBB (all in `Binaries\Win64`).
4. **The Direct3D path.** The game has D3D11 and D3D12 paths, and the
   `-dx11` and `-d3d11` switches pick D3D11. Try DXMT with `-dx11`, then Vulkan
   (vkd3d-proton) with `-dx12`. A fault that follows the backend belongs in
   the graphics work, not in FEX.
5. **Memory.** An Unreal title with a 124 MB image under a 16 GB FEX arena
   may hit the address-space limits in the runtime-risks plan. Check the
   `[footprint]` and `[va-exit]` lines against Hollow Knight's.

## Done when

- A `pp ui --play app-1654660 --until first-frame+20` reaches its first frame
  with the emulator and SteamStub removed.
- The cause of the fault is recorded in `docs/evidence/`, whether the fix is
  in the unwrap, a patch series or the runtime.

## Not in this plan

- Encrypted SteamStub, 3.0 and x86: phase 2 of the Steam plan, when a title
  needs them.
- Multi-process launches in general (the bootstrap is side-stepped, not
  supported).
