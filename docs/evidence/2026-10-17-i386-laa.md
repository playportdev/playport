# Large address aware for i386: Playport keeps the image's flag

**Date:** 2026-10-17. **Plan:** [Proton ARM64 alignment](../plans/finished.md#proton-arm64-alignment),
item B3 (runner item W6). **Linear:** [PLA-76](https://linear.app/playportdev/issue/PLA-76).
Source and workstation files only: no build, no phone, no game played.

## How Playport sets an i386 limit

A WoW64 child gets a 4 GiB window (`IOS_WOW64_WINDOW_SIZE`, `wow64_window.h`). How much of it
the guest may use comes from the owner image's own `IMAGE_FILE_LARGE_ADDRESS_AWARE` flag,
read through `ios_cur_image_info()->ImageCharacteristics` (madeira-unix 0063 and the window
patches before it; lines from the built `build/ntdll-unix` tree):

- `virtual_ios.c` `get_wow_user_space_limit` (7647–7656): `limit_4g - 1` if the flag is set,
  else `limit_2g - 1`. `HighestUserAddress` for wow64 is that minus one (15740), so
  wow64.dll and the guest see 2 GiB or 4 GiB.
- The window's own allocators clamp to the same value: thread stacks (16004), section views
  (16245) and anonymous VM (16346): `IOS_WOW64_WINDOW_SIZE` if LAA, else `0x80000000`.
- `env_ios.c` `map_nls_section` (2543): the NLS views take the same limit.
- `virtual_set_large_address_space` (17158–17164) keeps WineHQ's rule for an in-process
  i386 main image.

Nothing reads `WINE_LARGE_ADDRESS_AWARE`; no patch series names it.

## What Valve does

- Valve Wine bleeding-edge `c53678a`, `dlls/ntdll/unix/virtual.c` 5368–5413:
  `need_override_large_address_aware()` reads `WINE_LARGE_ADDRESS_AWARE` and is **on when the
  variable is unset** or `1`; `is_large_address_aware()` ORs it with the image flag and sets
  `user_space_wow_limit` to 4 GiB (WoW64) or frees the high 2 GiB (i386 host). The i386
  `kernel32` `GlobalMemoryStatus` (`dlls/kernel32/heap.c` 45–56, 482–490) stops clamping to
  2 GiB under the same variable. This is the code the plan cites as `799e5f0f`; the side
  copy's clone is shallow and does not hold that commit, so the code was read at `c53678a`.
- WineHQ 11.20 (`virtual.c` 3661–3679) has no override: the flag alone decides.
- The address-space reverts `b256c6e`, `4de2ea5` and `ed51707` (2026-10-14) remove
  `PROTON_LIMIT_ADDRESS_SPACE` and two per-game caps on the 64-bit user space at
  `0x700000000000`. They do not touch the LAA override, which is still in `c53678a`.
- Proton bleeding-edge `47c39230`, `proton` 1540–1542 and 1908–1912: `forcelgadd` is on
  unless the title's compat config has `noforcelgadd`, giving `WINE_LARGE_ADDRESS_AWARE=1`
  (else `0`); `noforcelgadd` titles (1344–1348): 2710 Act of War, 1621680 Sword and Fairy 4,
  888040 Metal Fatigue. None is in Playport's compatibility list.

## Result

Every i386 game executable checked carries the flag, so it already gets the 4 GiB window
and Valve's override would change nothing for it. The non-LAA images are a launcher, a tool
and an uninstaller. B3 is closed with this reason. Reopen it when a played i386 title's game
image lacks the flag and its guest allocations fail near 2 GiB.

A port would then be one helper (image flag OR an override) used at every site above,
plus Valve's `kernel32` `GlobalMemoryStatus` change as a `wine-pe` patch, gated on that
title and Hollow Knight on the phone.
