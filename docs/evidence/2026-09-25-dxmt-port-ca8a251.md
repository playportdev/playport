# Madeira 8c050d03: its DXMT commit ca8a251 re-ported onto upstream DXMT

**Date:** 2026-09-25. **Decision:** [0007](../decisions/0007-dxmt-on-upstream.md).
**Result:** the pins moved to Madeira `8c050d03`; Madeira's one new DXMT commit
is carried as `patches/dxmt-port/0045`. The dev IPA passes `verify-ipa` (60/60)
and `pp test`, and Hollow Knight reaches its main menu through the Play button
at 120 fps (HUD: `DXMT D3D11 FL_11_1 v0.80-295`). **Not verified:** gameplay
past the menu, the stale-binding probe with `stale-probe = 1` (it is off by
default), and the local geometry-emulation pipeline (ml1138) and fence-mode
control (ml1136) that `0045` carries unchanged (§2 item 5: nothing Playport
builds calls them).

`pp sync 8c050d0 --dry-run` replayed every series clean and held on two flags:
`dxmt-port-moved`, and a licence-file change in Wine. `pp sync` cannot land a
`*-port-moved` hold itself (it requires the row to equal the gitlink of the old
Madeira pin), so this update was landed by hand: the pin move, the Wine row, the
`dxmt-port` row and `patches/dxmt-port/0045` in one commit.

**The licence change.** Wine's `LICENSE-MADEIRA.md` gained a third-party
contribution (`feb96ad2be4`, xinput through win32u, by 125hz, under the DCO) and
reworded its provenance paragraph. The licence stays LGPL-2.1-or-later and the
notices copy the file whole, so nothing in `LICENSING.md` or `NOTICES.md`
changes. Playport ships its own XInput DLLs in place of Wine's (provenance
P6-xinput), so the contributed code is built but not what games load.

## 2. The re-port: `patches/dxmt-port/0045`

Madeira's `ca8a251` ("placement-heap buffers, a released-object record for
native faults, optional stale-binding check") cherry-picked onto the series with
conflicts in four files. `Rebased: resolved`.

1. **Two new unix calls that upstream already has.** Madeira added
   `MTLDevice_heapBufferSizeAndAlign` and `MTLHeap_newBufferAtOffset` at its
   slots 139-140. Upstream DXMT has `MTLDevice_heapBufferSizeAndAlign` (slot 126,
   returning `struct WMTSizeAndAlign`) and `MTLHeap_newBuffer` (slot 128, with an
   offset), both remote-guarded by `wmt_remote_guard.h` to answer 0, which is
   Madeira's remote behaviour. The slots are not carried:
   `MTLHeap_newBufferAtOffset` is a PE-side wrapper over `MTLHeap_newBuffer`, and
   Madeira's out-parameter `MTLDevice_heapBufferSizeAndAlign` is replaced by
   upstream's (C has no overloads; only Madeira's `madeira_d3d12.dll`, which
   Playport does not build, calls that form).
2. **What merged cleanly but was wrong.** Git appended Madeira's two
   `_wow64` stubs to the end of the wow64 table (slots 150-151, with no native
   twin) and its two names to `wmt_api_names.h`. Both were dropped; the table
   stays at 150 slots. `gen_remote_guard.py` and `gen_api_names.py` rerun in the
   tree reproduce the committed files unchanged, and `pp slots` reports every
   call matching its slot.
3. **The stale-binding probe on upstream's bodies.** Madeira hooked its own
   placement-heap and residency-set unix bodies, which the first rebase had
   replaced by upstream's. The hooks moved to upstream's `_MTLHeap_newBuffer`
   (a new buffer at a recycled address is alive) and
   `_MTLResidencySet_addAllocations` (each allocation checked). The six
   geometry-emulation draw checks sit before upstream's named binding indices
   (`SM50_BINDING_INDEX_INDEX_BUFFER`, `_INDIRECT_ARGUMENTS`).
4. **Taken as is.** The released-object ring (`madeira_wmt_released_class`),
   the probe itself (off unless `madeira.cfg` `stale-probe = 1`) and every other
   binding-point check applied without conflict, as did the two pieces in item 5.
5. **Carried unchanged, with no caller in Playport.** `0045` also carries two
   pieces of `ca8a251` its message does not name. ml1138: the local backend
   builds geometry-emulation pipelines in
   `_MTLDevice_newGeometryEmulationPipelineState` instead of refusing them.
   ml1136: `MadeiraCtl` op 6 and `madeira_set_fence_mode`. Nothing Playport
   builds or ships calls either: their only callers are in Madeira's
   `madeira_d3d12.dll` (the IR-converter D3D12 path), which Playport does not
   build; DXMT's own D3D11 geometry emulation (`d3d11_pipeline_gs.cpp`) does
   not use that unix call, and the app has no `madeira_set_fence_mode` caller.
   No run exercised them, and none can in Playport today.

## 3. Build fixes the move needed

- **A moved pin was not in an existing run clone.** `stages/unix.sh` and the
  `pe` stage clone Madeira and Wine once and never fetched, so the first build
  after the move failed with `unable to read tree`. Both now fetch the pin when
  the clone lacks it, as `dxmt-base.sh` already did. `pp sync` builds in fresh
  directories, so it never hit this.
- **Winios gained a file.** Madeira's `Winios.h` now includes
  `WiniosGamepad.h`, and its `libwin32u_unix.a` calls
  `winios_gamepad_get_state`, defined in `WiniosGamepad.c`. Both are staged
  into `Sources/WinIOS/` under P5-winios. Madeira's own XInput DLLs, which read
  that snapshot, are still replaced by Playport's (P6-xinput), so no pad
  reaches it; it answers "not connected".
