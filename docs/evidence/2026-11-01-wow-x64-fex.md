## Fixes made on the way

- **madeira-unix 0274.** `Wow_loader.dll` copies its image into a pagefile section and maps it twice
  (read-write and read-execute) over its own image range. `mprotect_exec` backed the read-execute view
  with a JIT-pool slot (vm_remap), detaching it from the section, so it held zeros. In an ARM64EC process a
  section's view now keeps the section's memory (read, plus write when asked; the host never runs x86-64
  code). Log: `[anon-view] section view 0x73f8f70000+0x2030000 keeps its section's memory, r-`.
- **wine-pe 0059.** Only an image's view reached FEX's executable intervals, so the read-execute view
  decoded as NOEXEC. An executable view of a plain section is now told to FEX as a protection change
  (`[map-notify] executable view of a plain section … told to FEX`).

## The open blocker: `int3` in Wow_loader on the main thread

- Just before it the client writes 8 bytes at ntdll+0xca5a0, which is `pWow64PrepareForException`
  (`[exec-req] #2 addr=…EAA5A0 size=8 new_prot=40`): it hooks exception dispatch through the pointer the
  x64 `KiUserExceptionDispatcher` reads. It then calls `Wow_loader.dll`+0x125bf0, a fatal routine that
  calls `+0x1e4f200` (prologue, then `int3`); its SEH handler (`+0x20069b4`) starts `BlizzardError.exe`.
- Desktop Wine 11.20 with the same build's `Wow.exe` and `wow_loader.dll` (12.1.5.70688, copied off the
  phone into `.work/wowdesk`) reaches the login screen. Its first breakpoints are at `+0xaa2680` on a
  worker thread, caught by the same handler and unwound; the main thread never reaches `+0x125bf0`.
- Lead, not yet tested: Wine's ARM64EC x64 `KiUserExceptionDispatcher` thunk calls the hook and then
  `ret`s back to the ARM64EC dispatcher, while x64 Windows (and Wine's x86-64 one) go on to
  `RtlDispatchException` in the same x64 code. A client that parses that code to find its continuation
  may fail here. Other candidates: what the client checks of ntdll's x64-visible code, CPUID or timing
  under FEX. Desktop decrypted dump: `.work/wowdesk/runs/desk-dump/loader.bin` (base-relative).

## The Wow64PrepareForException hook (wine-pe 0060)

**The probe: `tools/compat/probes/exchook.c`** (llvm-mingw x86-64, `exchook.exe` sha256
`6b1c299cd696064881fe5587e6c0e32509adb3f2ae04b91366d1b0ace8f8683d`, 81,408 bytes). It finds the
hook's pointer through the `mov rax,[rip+x]` after `cld` in the x64 code of ntdll's
`KiUserExceptionDispatcher` export, as the client does, stores an x64 hook there (VirtualProtect to
read-write-execute, as the client asks) and a vectored handler, then checks against x64 Windows:
(a) the export's code: the hook's call is followed by a dispatch call in the same code; (b) int3: the
hook runs first with rsp+8 = the context, rcx = context+0x4f0, its return address in the export, a
machine frame at context+0x590 holding Rip and Rsp; code `80000003`, ExceptionAddress and Rip both the
`int3` itself (x64 Windows backs Rip up over it: Wine's x86-64 `Rip--`), Rsp and the registers as set,
and the handler then gets the same record and context; (c) the hook's change to the context reaches
the handler and the resumed code; (d) the same for an access violation reading 0x10; (e, f) the hook
resumes by itself with `RtlRestoreContext` / `NtContinue` and no handler runs; (g) b on another
thread; (h) the pointer put back: the handler alone.

**Why the hook never ran.** ntdll's ARM64EC code runs from its JIT-pool copy and reads that copy's
`.data`; x86-64 code runs at the image's own addresses and reads the image. The guest's store reached
the image only, so the dispatcher read `pWow64PrepareForException` = 0 and dispatched directly
(after the fix, `[ki-path] … hook=<the probe's hook> slot=ntdll+0xca5a0 ec=0000000000000000`: the
pool copy still holds 0). Where it was called, the x64 thunk called it with its own frame (context
at rsp+0x30, the record past the ARM64 context) and returned to the ARM64EC dispatcher.

**wine-pe 0060.** `prepare_exception_arm64ec` reads the hook and the export's bytes at the image's
address; when either is set it lays out x64 Windows' frame (the record at context+0x4f0, the machine
frame at +0x590) and enters the export with rsp at the context (a two-instruction x64 entry drops the
return address the ARM64EC-to-x64 call pushes). The export is now x64 Windows' code, as in x86-64 Wine:
`cld`, the hook's `mov`, the call with rcx = record and rdx = context, then `dispatch_exception`, with
the x86-64 unwind information. Nothing changes for a process with no hook and an unpatched export.

## The per-page stream, compared with desktop Wine (fex 0090, 0091; wine-pe 0062; madeira-unix 0276–0278)

**Run 20261101T172555 was a loop, not a per-fault cost.** 43 distinct code pages faulted once each; then one
address, `Wow.exe`+0x89B3FFF, faulted 441,337 times until the run ended. An instruction starting on the last
byte of an executable page ran into the next, still inaccessible page: FEX decoded it as PartialDecode and the
access violation reported Rip in ExceptionInformation[1]. x86-64 Windows reports the first byte outside (the next
page); the client's handler made Rip's page executable again and the fault repeated. The read of address 0 before

## A no-access page beside open code inside one 16 KB host page (madeira-unix 0279)

**Cause of run 20261101T182709's `c0000005` at `0x15AD75050`.** It is not inside `Wow.exe` (image
`0x141800000+0x7354000`): it is the image base plus `0x19575050`. Desktop Wine with the same `Wow.exe`
(decrypted image copied from the running process at 20 s and 45 s, scratch tooling under
`$PLAYPORT_BUILD/wowdesk/reloc`) shows the code at `Wow.exe+0x2DA119`, the last page the phone opened, is
ordinary compiled code that indexes jump tables (`lea r13,[image base]; mov edx,[r13+rcx*4+…]; add rdx,r13;
jmp rdx`). Desktop opens `+0x2DB000` next; on the phone no fault for that page came, and `0x19575050` is
the 32-bit value at file offset `+0x2DB590`, the page's still-encrypted bytes. With diskCache off (run
20261101T184550, image at `0x140C60000`) the target was again base `+0x19575050`, so the disk cache is
not involved. The client's code page and the closed page next to it share one 16 KB host page, whose
protection was the union of its four 4 KB pages: the read of the closed page did not fault, so the client's
hook never opened it, and the client jumped through encrypted bytes. On x64 Windows (and desktop Wine)
that read faults and the hook opens the page first.

- **madeira-unix 0279** (`ios-port`): a host page holding a committed no-access 4 KB page (not a guard page)
  beside a page with EXEC is kept `PROT_NONE`; the Mach exception handler completes an access to its
  accessible pages through a transient alias with the load/store emulators (FP/SIMD `LDP` added for
  memcpy's `ldp q0, q1`) and declines an access to the no-access page, which then raises the guest's access
  violation. A read by a thread that holds FEX's code lock (FEX translating guest code that another thread
  is closing) is completed for any committed page. Decisions in `pp_noaccess_split.h`, host test
  `tools/tests/test_noaccess_split.py`.

## FEX's code reads and the client's reads from a read-only alias of the view (madeira-unix 0280, 0281; fex 0092)

**What the 21.4 M reads of run 20261101T191349 were.** Its `[noaccess-split]` lines sample every 4096th emulated read
(5,240 samples). About a third were FEX's own: the decoder's byte reads in `libarm64ecfex.dll` (`ldrb`) and the byte
loop of ntdll's `memcpy` under its `ReadData`. About two thirds were the client's own reads from translated code
(`LDAPUR`/`LDAPURB`/`LDR`/`LDP`, 1 to 32 bytes) of data on its open code pages. The row above that calls them nearly all
FEX's decoder is wrong. The code is not `Wow.exe`'s image view: its loader maps a pagefile section over the image range
(`[anon-view] section view 0x…+0x7354000 keeps its section's memory`, madeira-unix 0274).

- **madeira-unix 0280** (`ios-port`): when a host page of a mapped view (image or section, never a plain allocation,
  whose decommit replaces its memory) first becomes noaccess-split, `mprotect_range` makes a read-only alias of the
  whole view (`mach_vm_remap` of the same memory, then `mach_vm_protect` read). It sends the alias to every emulator
  through `BTCpu64IosAddAliasMapping` with bit 63 of the size set. `delete_view` retires and frees it. Log:
  `[code-alias] view 0x…+0x7354000 has a noaccess-split host page: read-only alias 0x…`.
- **fex 0092** (`ios-port`): a query-only table of these aliases, under a sequence count. The decoder's byte source
  (`AdjustAddrForSpecialRegion`, as for sub-floor code) and the disk cache's hashing (`GuestCodeBytes`) read guest code
  there. Guest addresses, block identity, executable-range questions and the guest's own accesses are unchanged, so a
  read of the closed 4 KB page still faults. Log: `[iOS-code-read]`.
- **madeira-unix 0281** (`ios-port`): the Mach handler completes the guest's read of an open page that a view's alias
  holds from that alias. Writes and reads outside such a view keep the transient remap. The handler also sets the NEON
  state only when the load changed it. `pp_code_alias.h` holds the lookup, with host test
  `tools/tests/test_code_alias.py`.

## After sign-in: the main thread's spin, and read stubs for hot sites (madeira-unix 0282, 0283)

**What the owner's sign-in showed (20:33 launch, IPA `b2f06917…`).** Battle.net logon, realm join and the game
server's `Handle Auth Response: 0` / `Glue Authed To WoW: 0` came at 20:39:59, and General.log switched the screen
from `login` to `charselect` 0.5 s later. Nothing more followed; at 20:48 the screen still said "Logging in to game
server". Sampled live:

- The main thread was in one function for every sample after 20:39:59 (45 of 45 in the `[thread-sample]` bursts,
  guest rip `Wow.exe`+0x329919f, the same function TACT task threads used during start-up). It made about 26,000
  `RtlEnterCriticalSection`/`RtlLeaveCriticalSection` calls and 1,600 yields a second, and about 48,000 reads a second of
  one dword at `Wow.exe`+0x32992a4 on an open 4 KB page of a noaccess-split host page. Each was a Mach exception. The
  exception thread used ~63 % of a core and wineserver ~45 %. The main thread was at ~30 % and spent the rest waiting on
  those exceptions. It still took new code-page faults (564 in 8 minutes), so it was moving, just very slowly.
- KUSER_SHARED_DATA reads (`0x7ffe0004`, `0x7ffe0320`) through the same handler: ~4,300 a second.
- The game connection (port 3724) got the auth exchange (tx 7/1,071 B, rx 12/8,191 B), then 21 small server packets
  over 88 s with **nothing sent by the client** (`[sock-tl]` `tx=0/0B`), and was gone by 20:42:57. The client had not
  yet asked for its character list.
- Desktop Wine has no sign-in to compare: `.work/wowdesk` runs never signed in, and the secrets are typed only
  through `pp ui --secret-file`.

**madeira-unix 0283** (`ios-port`): the Mach handler counts the reads it completes for the noaccess-split service
(through a view's alias) and the sub-floor service (KUSER_SHARED_DATA) per JIT pc. On the 256th read from one site
whose load it can make (`LDAPUR{B,H,,}`, `LDUR`, `LDR` unsigned offset; general register; no sp or x18 base), it does
two things. It writes a stub into a pool region within branch reach (`ios_jit_stub_region`, carved below the tail and
never handed to FEX). Then it writes an aligned `B` over the load. The stub (`pp_split_stub.h`, host test
`tools/tests/test_split_stub.py`, which disassembles one stub with llvm-mc) saves two scratch registers on the host
stack. Without touching the flags, it checks that the address is in the window and aligned, and, for a view, that
Wine's vprot byte of the 4 KB page is committed, not a guard page and accessible. Then it loads from the alias (`LDAPR`
