## 1. What each thread takes

FEX's band is one 16 GB range, `[0x7c00000000, 0x8000000000)`, that ntdll
reserves at start and serves only to FEX's requests. Madeira-unix 0038 counts
its views (`title: band:` lines; `pp ui`'s result `band`), and fex 0009 with
rpmalloc 0001 logs each thread's start (`[band]` lines).

Every emulator thread's start took the same, in every run:

- **rpmalloc: 32 MB in 3 mappings.** The thread's heap (64 KB) and two
  16 MB spans, one for small blocks and one for medium ones. Most of both is
  untouched VA.
- **Call-return stack: 16 MB and two guard pages** (16,392 KB).
- **L1 lookup cache: 2 MB.** The plan names the per-thread `VirtualMemSize` of
  8 GB and the L2 cache. The L2 cache is off on iOS (FEX's `DisableL2Cache`
  defaults to true), so its 16 MB table for the 8 GB and its 32 MB backing
  are never mapped (`[lookup-cache] ml606 mode=l1-only alloc=2MB`).

That is 50 MB. With main's placement a thread took about 64 MB of the band
(the thread states were 64 MB apart). Each call-return stack ends 64 KB past a
16 MB boundary, so the next 16 MB-aligned span skipped almost 16 MB. Only small
views could use that hole.

## 2. The leak: 3.7 GB before the first frame

On `d5fc3c04` the second thread's start logged
`rpmalloc +3728MB in +465 maps`: 233 small spans and 232 heaps, a quarter of
the band, before Hollow Knight showed its first frame. After that, each of the
next 50 threads added its 32 MB. At 50 threads the band held 7,086 MB, with a
largest free range of 8,768 MB (DXMT, the main menu). On Vulkan with DXVK's own
thread count, it held 7,294 MB at 54 threads.

The cause, found with two probes (builds of their own: the branch's rpmalloc
0001 keeps only the counters, and logs no `[rpm-heap]` or `[rpm-span]` lines):

- **Heaps.** `2e6f7ed8` logged each heap made. Heap 3 onwards came from one
  thread (thread 0x28, as it started), and each came from a chain of
  `FEXCore::Allocator::malloc` frames one shorter than the one before: 231 at
  heap 3, 230 at heap 4, and so on, down to `ThreadInit`. That is one
  recursion 231 levels deep, unwinding.
- **Spans.** `30186e97` logged the size class behind each new small span. All
  233 were class 4 (64-byte blocks), on one heap, and each saw the same span
  count: the same recursion, one level per span.

What recurses: every mapping rpmalloc makes names itself through
`rp_name_hook`, which on iOS is FEX's `VirtualName`. `VirtualName` logs each
name, for the first 256 names in the process (`[vname]`, an old Madeira
probe), and the log allocates. So an allocation that needs a new mapping
allocates again before rpmalloc has recorded that mapping:

- on a thread that has no heap yet, the nested allocation makes a heap, whose
  mapping names itself, and so on;
- on a heap with no partial span for the size class, the nested allocation
  maps a span, and so on.

The log's cap (about 231 names were left when thread 0x28 started) ends the
recursion. On the way back, each level sets its own heap as the thread's, and
its own span as the heap's partial one. So each of the 233 spans kept the one
64 KB page it gave out, and lost the other 255.

**Fix (rpmalloc 0002).** rpmalloc names none of its mappings on iOS, where a
name does nothing but that log. On `8ef67e3e` the same start logs
`rpmalloc +32MB in +3 maps`, with 3 heaps made in the process by then, not 234.

A first guess, that x18 made `TlsGetValue` read an empty TLS slot, was tested
on IPA `756f295a` (`756f295aaab9f9263875c939c098171a2a3552fe48689c73308121578872367c`),
which read the slot both ways and counted the differences. It counted 0, so
that guess was dropped.

## 3. Placement (fex 0010)

Call-return stacks are now reserved with `MEM_TOP_DOWN` inside the band, so
they pack at its top while rpmalloc's spans fill it from the bottom. Wine takes
`MEM_TOP_DOWN` together with address requirements (Windows does not). The
final map shows them as one run, `0x7fcdce0000: 13052MB free, then
50 x 0x1002000`, and the rest of the band with no hole of more than 64 KB. The
band's free space outside its largest free range fell from 530 MB
(`d5fc3c04`: free 9,298 MB, largest 8,768 MB) to 7 MB (`4aab2dd5`: free
13,059 MB, largest 13,052 MB).

## 5. On the phone

- **The standard play** (`pp ui --play app-367520 --until first-frame+10
  --shot`, `4aab2dd5`): JIT 3.15 s, game start +3.74 s, first frame +9.69 s,
  then the main menu. `limits` all 0.
- **Hollow Knight's video** ([hk-video](2026-09-26-hk-video.md)'s case; `pp ui
  --play app-367520 --pad --until first-frame+25 --leave-running`, then
  Start Game and A on the profile screen's cursor, slot 2, which was empty;
  `8ef67e3e` and `7d44215e`). The prologue poem, the opening cinematic, then
  King's Pass with the Knight in control. 51 threads, nothing refused. The
  final IPA changes only the Vulkan backend's environment, so this was not
  played again on it. The game was ended before it saved, so slot 2 is still
  empty, and the cursor stays on slot 2, where it was before these runs.
- **A DXVK game with DXVK's own thread count.** Hollow Knight on the Vulkan
  backend (`--settings 'app-367520:{"graphics":"vulkan"}'`, `4aab2dd5`; no
  `DXVK_CONFIG` any more): `DXVK: Using 6 compiler threads`. All six
  `dxvk-shader-*` threads and `dxvk-frame` start. It reaches the main menu at
  120 FPS (+15 s, screenshot). 53 threads, 3,484 MB, nothing refused. No other
  DXVK title is installed. The Witcher 3 is installed, but on Vulkan it stops
  after its first frame (decision 0015's known gap), so it was not used.
- **Vulkan freezes in play, with 2 compiler threads as with 6.** The band is not
  the cause. Four Vulkan runs of this session stopped, all with the band
  refusing nothing and more than 8 GB free:
  - `s1-vk`, 6 threads (`d5fc3c04`): during the menu's fade-in;
  - `s2b-vk2`, 2 threads, the `DXVK_CONFIG` main set (`d5fc3c04`): at the
    same point;
  - `s4-vk`, 6 threads (`ca49d120`, a probe build): after Start Game;
  - `s9-vk`, 6 threads (`8ef67e3e`): during the fade-in.

  In every one of them, every guest and DXVK thread waits in
  `os_sync_wait_on_address`, and Wine's API counters drop to zero within a
  second. DXMT plays of the same IPAs do not stop. The freeze does not depend
  on the thread count, so this record keeps it apart from the band. It needs
  its own investigation, and until then a Vulkan play past the menu is not
  shown.

## 6. Not done

- The Witcher 3's `jumbo-mb` holdback reserves guest address space below the
  band. It is not the FEX band, and nothing here changes it.
- `pp perf` was not run. Nothing here changes code on a frame's path. The census
  (every 2 s, on the app's thread) walks the band's views in Wine's view tree
  under `virtual_mutex`, from the first one in the band, and the band now has
  about 360 views.
- The main thread's call-return stack is reset thousands of times in the
  first minute (`[callret] ml610 resets=16384`, `[span-census]` lines). That
  is a cost in time, not in the band, and it is not looked at here.
