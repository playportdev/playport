# FEX without AFP: why Hollow Knight is black, and three FPCR modes to test (fex 0080)

**Linear:** PLA-320 (Hollow Knight black without AFP), PLA-364 (RDR2 gameplay CPU: AFP off is in its
default). **Patch:** fex 0080. **IPA:** dev, `Playport-26.5-9a80a09d.ipa`, sha256 `9a80a09dfff29cba97aaa9bcfb27d6a8273d9161c597b1e6b8166703b57cff8f` (side worktree build).

**Phone results:** [afp-fpcr-and-qpc](2026-10-21-afp-fpcr-and-qpc.md) (`fiz`, `ah` and `ahx` each show Hollow Knight's menu; `fiz` is every game's default by decision 0154). **Phone gates not run here.** This was built and checked on the host only, in the side worktree `.work/worktrees/afp`
(decision 0117), while the main checkout had the phone. The default (`MADEIRA_FEX_AFPOFF_FPCR` unset)
behaves as before, so no game changes until a mode is chosen.

## 1. The black screen is AFP off alone, and has been since 13 October

Hollow Knight (Unity 6, Direct3D 11 on DXVK and Vulkan) with `env.FEX_HOSTFEATURES=disableafp` runs at
60 fps with normal GPU time and draws black: at first frame +10 and +25 on dev IPA d4ff7de2
(`.work/ui-runs/20261021T154858`), with the menu under `enableafp` (`20261021T155324`).

The 13 October bisect recorded `disableafp` alone as passing. Its screenshots (`20261013T063943`,
`20261013T064052`) are black too. Their FEX line is the same as today's: `AFP=0 LRCPC2=1`, the Mono
bridge armed and never activated. So the black needs only AFP off; the rows and the later "AFP off
and the bridge route" conclusion are corrected in
[2026-10-13-host-cpu-features.md](2026-10-13-host-cpu-features.md) and
[2026-10-13-a12-profile-mono-smc.md](2026-10-13-a12-profile-mono-smc.md). It predates fex 0059's
lean ExitFunctionEC (20 October), which runs only without AFP, and it does not depend on which route
Mono's backpatcher is found by.

## 2. What AFP off changes in FEX

Line numbers are in the patched tree (`$PLAYPORT_BUILD/run/fex` before fex 0080). Neither Madeira nor
Playport changed FEX's floating-point code generation: no added line between the `fex` pin and the
tree's head emits an FP arithmetic, conversion or min/max instruction.

**Scalar SSE keeps the upper lanes (candidate (a): not the cause).** `HostSupportsAFP` picks the
form in `VFScalarOperation` (`FEXCore/Source/Interface/Core/JIT/VectorOps.cpp:296-363`),
`VFScalarUnaryOperation` (369-425) and `VFScalarFMAOperation` (265-290). With AFP, FPCR.NEP makes
a scalar instruction insert into its destination. Without AFP, the result goes to `VTMP1` and an
`INS` puts lane 0 into a copy of the first source, for every op built on them. That covers
addss/subss/mulss/divss (196), min/max (442-492), sqrt/rsqrt/rcp (495-586), cvtss2sd and cvtsd2ss
(589-632), cvtsi2ss (635-737), roundss (740-764) and cmpss (767-924). This is FEX's normal path on hosts
without AFP.

**min/max NaN and zero order (candidate (c): not the cause).**
- minss/maxss without AFP are `fcmp` + `fcsel` (VectorOps.cpp:449-455, 477-483), x86's "first operand
  only if strictly less/greater". `SaveNZCV` treats them as flag clobbers (`OpcodeDispatcher.h:1302-1310`).
- minps/maxps are `fcmgt` + `bif`/`bit` (1446-1465, 1505-1524). With AFP, all of them are
  `fmin`/`fmax` under FPCR.AH.

**FPCR is what differs (candidates (b) and (d)).** With AFP:
- `FillSpecialRegs` (`Arm64Emitter.cpp:670-695`) sets FPCR.NEP and FPCR.AH on every entry to JIT code,
  and FIZ from MXCSR.DAZ after a runtime call (`SetFIZ`).
- `SpillStaticRegs` (713-731) clears NEP, AH and FIZ before one, and `SetRoundingMode`
  (`MiscOps.cpp:148`, LDMXCSR, FXRSTOR, XRSTOR) inserts FIZ.
- ExitFunctionEC (`Module.S:470-481`) clears NEP and AH for ARM64EC code.

Without AFP none of these run, so x64 code runs with AH=0 and FIZ=0. Per the Arm ARM's AFP behaviour,
x86 code then sees:
- an invalid operation (0/0, inf-inf, sqrt of a negative) gives the default NaN with the sign clear
  (+NaN, 0x7FC00000), where x86 gives -NaN (0xFFC00000);
- with two NaN operands, ARM's order applies (a signalling NaN first) rather than x86's (the first
  operand);
- MXCSR.FTZ (FPCR.FZ) flushes denormal inputs as well as outputs, i.e. FTZ acts as FTZ+DAZ;
- MXCSR.DAZ without FTZ is not applied.

FPCR's FZ and rounding mode are the same in both cases (`SetRoundingMode` writes them either way).
Which of these Hollow Knight trips was not found on the host: there is no AArch64 machine or emulator
here. fex 0080 lets the phone answer it.

**Madeira.** Madeira has had AFP off by default since FEX `aaf73a9` (`CPUFeatures.cpp`, 3 October;
in `upstream/madeira`'s FEX at `origin/HEAD` `f59cab9`). Its FEX history from our `fex-port` base to
there has no FPCR, MXCSR or scalar-SSE change (`git log 0f8edf8..f59cab9`: alias table, call-ret
stack, transitions, Mono bridge), so there is no Madeira fix to port.

## 3. fex 0080: `MADEIRA_FEX_AFPOFF_FPCR`

Only without AFP, read at process init before the dispatcher is emitted (`IosAfpOffFpcr`,
`Arm64Emitter.h`). FPCR.NEP is never set; FEX's insert code stays.

| Value | FPCR for x64 code | ARM64EC code sees | FPCR writes |
| --- | --- | --- | --- |
| `0` (default) | as the thread has it | the same | none (today) |
| `fiz` | FIZ = MXCSR.DAZ | FIZ (as with AFP, where ExitFunctionEC leaves FIZ) | LDMXCSR; after a runtime call only when FIZ differs (a context restore clears it) |
| `ah` | AH, FIZ = MXCSR.DAZ | AH and FIZ | LDMXCSR; on entry only when AH is missing (a new thread, a reset FPCR), so none per transition |
| `ahx` | AH, FIZ = MXCSR.DAZ | neither (cleared on leaving) | two per x64 <-> ARM64EC transition, as with AFP; keeps ExitFunctionEC (the lean exit leaves FPCR alone) |

- **`fiz` and `ah`** read FPCR, compare and branch (no flags), and write it only when it differs:
  `FillSpecialRegs` (`Arm64Emitter.cpp`) is `mrs`, `ldr` MXCSR, `ubfx`, (`orr` AH), `eor`, `and`,
  `cbz`, then `eor` and `msr` only if needed. EnterEC under `ah` is `mrs` + `tbnz`.
- **`ahx`** mirrors AFP less NEP: `FillSpecialRegs` sets AH (+FIZ) and `SpillStaticRegs` clears
  AH and FIZ. ExitFunctionEC's existing `tst #6` clears AH (NEP is never set).
- **`SetRoundingMode`** inserts FIZ under every mode, and AH under `ah`/`ahx`.
- **The disk cache's process bucket is keyed on the mode**, because `SetRoundingMode` and
  `FillStaticRegs` are compiled into blocks. *Correction (fex 0081,
  [afp-fpcr-and-qpc](2026-10-21-afp-fpcr-and-qpc.md)):* 0080's key read `IosAfpOffFpcr` before
  ProcessInit set it, so it was always 0; 0081 keys on the variable itself.
- **The log line** is `FEX: afpoff-fpcr mode=N (value)`, then `ec-exit-lean-v1 … enabled=false`
  under `ahx`.

## 4. What AH=1 changes for ARM64EC and host code (`ah`)

Under `ah`, DXVK, vkd3d-proton, Wine's ARM64EC DLLs and the unix side (KosmicKrisp, Wine's
syscall paths, which save and restore FPCR but do not reset it) run with FPCR.AH=1. In the Arm ARM's
pseudocode for FEAT_AFP (FPDefaultNaN, FPProcessNaNs, FPMax/FPMin, FPMaxNum/FPMinNum, FPUnpack,
FPRecipEstimate, FPRSqrtEstimate, BFloat16 ops), AH=1 means:
- **default NaN:** the sign is set (-NaN);
- **NaN operands:** x86 order (the first NaN operand, signalling or not, before the second);
- **FMAX/FMIN** (scalar, vector, pairwise, across lanes): op2 when either input is NaN or both are
  zeros, with no IEEE NaN handling. **FMAXNM/FMINNM** keep "number over quiet NaN"; two zeros of
  opposite sign may give op2 rather than the IEEE-signed one (to check);
- **FZ:** flushes outputs only, after rounding; inputs are flushed only by FIZ;
- **FRECPE/FRSQRTE/FRECPX:** denormal inputs are not flushed by FZ, and with FEAT_RPRES the estimates
  have 12 bits;
- **BFloat16 conversions and dot products:** behave as FEAT_EBF16's alternate behaviour describes;
- **FABS/FNEG** of a NaN leave its sign as it is.

Arithmetic on non-NaN, non-denormal values is unchanged. (From the Arm ARM text as recalled for this
change; check against DDI0487 before recommending `ah` as a default.)

Our native code, searched:
- **Mesa (KosmicKrisp and NIR constant folding):**
  - no NEON `vmaxq_f32`/`vminq_f32` or `fmaximum`/`fminimum` in `src/` (outside tests);
  - NIR folds `fmin`/`fmax` through `util_min_num`/`util_max_num` (`src/util/u_math.h:350-372`), which
    handle equal zeros themselves before C `fmin`/`fmax` (FMINNM/FMAXNM), so AH's zero order does
    not reach them;
  - `fmin(fmax(...))` in the float-to-int conversions (`nir_opcodes.py:425-430`) clamps numbers;
  - no `-ffast-math` in `build/stages/mesa.sh`.
- **DXVK** uses `std::fmin`/`std::fmax` once (`src/util/util_math.h:31`, a clamp: FMINNM/FMAXNM)
  and no SSE/NEON min/max intrinsics. vkd3d-proton has none either.
- **Not searched:** Wine's ARM64EC DLLs and Apple's frameworks (Metal, libm) are compiled code we
  cannot audit here. Metal's shader compiler runs in its own process (FPCR is per thread).

## 5. Phone test for the main checkout

After the `afp` branch is moved into the main checkout and installed (`./pp install`), each run stops
when its screenshot answers it. The Hollow Knight runs, menu or black:

```sh
./pp ui --settings 'app-367520:{"runtime":"env.FEX_HOSTFEATURES=disableafp env.MADEIRA_FEX_AFPOFF_FPCR=fiz"}' --play app-367520 --until first-frame+25 --shot
./pp ui --settings 'app-367520:{"runtime":"env.FEX_HOSTFEATURES=disableafp env.MADEIRA_FEX_AFPOFF_FPCR=ah"}'  --play app-367520 --until first-frame+25 --shot
./pp ui --settings 'app-367520:{"runtime":"env.FEX_HOSTFEATURES=disableafp env.MADEIRA_FEX_AFPOFF_FPCR=ahx"}' --play app-367520 --until first-frame+25 --shot
```

Check the title process's `FEX: afpoff-fpcr mode=` line (1, 2, 3) in the pulled log. Then run the
smallest mode that shows the menu on RDR2 at the porch: its compat default
(`jumbo-mb=8960 env.PLAYPORT_VK_HEAP_MB=3072 env.MADEIRA_FASTSYNC_SEM=1 env.FEX_HOSTFEATURES=disableafp
env.MADEIRA_X64_CS_FASTPATH=1 env.MADEIRA_FEX_BATCH2=1`) plus `env.MADEIRA_FEX_AFPOFF_FPCR=<mode>`,
with the usual `--pad --action set:donorPoolMB=auto --settings 'app-1174180:{"aspect":"16:9",...}'
--until first-frame+300`. Compare fps per E-GHz against the default runs d2 to d5 (10.4 to 10.6). `fiz`
and `ah` should cost nothing measurable; `ahx` pays two FPCR writes per transition, as AFP does.
