# Hollow Knight's cinematics: why they are black, and GStreamer for Media Foundation

**Date:** 2026-09-26. **Tree:** branch `research/hk-video` off `origin/main`
`d6a5180`. **Build:** rebased onto `origin/main` `8f9dd12`; dev IPA sha256
`87657d779d3150b4b59010c46e8476d23f6780078a349c1aec63e1e5995038c1`
(`verify-ipa.py`: 63 checks passed), built in a worktree, so its DXMT and FEX
PE hashes are path-dependent and differ from a main-checkout build.
**Phone:** iPhone Air (`iPhone18,4`), iOS 27.0, 2026-09-27; sections 6 to 8.

**Result:** Hollow Knight's cinematics are H.264/AAC MP4 clips that Unity
plays through Media Foundation. The app shipped none of Wine's media sources
or decoders and no unix side for winegstreamer, the only decoder Wine's Media
Foundation has, so every clip failed to open
(`WindowsVideoMedia error 0xc00d36c4`, `MF_E_UNSUPPORTED_BYTESTREAM_TYPE`)
and the screen stayed black until the player skipped it. The branch adds
winegstreamer with a statically linked GStreamer, as Proton, CrossOver and
Winlator do.

## 1. What the game plays

`MFCreateSourceResolver`, `MFCreateSourceReaderFromURL`, `MFTEnumEx`,
`MFCreateDXGIDeviceManager` (its imports from `mfplat.dll` and
`mfreadwrite.dll`). The installed game on the phone
(`Documents/prefix/drive_c/Games/Hollow Knight/hollow_knight_Data`, listed
and read over AFC, read-only, under the device lock) has no loose video

## 2. Why nothing opened them

- Wine 11.18's source resolver (`dlls/mfplat/main.c`
  `resolver_get_bytestream_handler`) tries the registered byte stream handler
  for the extension or MIME type and then winegstreamer's. The app staged
  only `mf`, `mfplat`, `mfreadwrite` and `rtworkq` (the set Madeira ships):
  no `mfsrcsnk`/`mfmp4srcsnk`, no `winegstreamer.dll`, and no
  `ByteStreamHandlers` or `MediaFoundation\Transforms` keys in the prefix
  seed.
- Wine's configure found neither GStreamer nor FFmpeg ("gstreamer-1.0 base
  plugins development files not found", "FFmpeg development files not found"),
  so winegstreamer was not even built. `winedmo`, Wine's FFmpeg path, only
  demuxes; every decoder MFT (`msmpeg2vdec` for H.264, `msauddecmft` for
  AAC) is a front end to winegstreamer's. Wine's PE-side FFmpeg
  (`libs/ffmpeg`) has no codecs. So GStreamer is required for any video.

## 3. What others do

Proton ships winegstreamer with a full GStreamer (its separate
media-converter was folded into winegstreamer); CrossOver and the macOS
wrappers ship `GStreamer.framework` (CodeWeavers' support page names missing
libav plugins as a cause of broken game video); Winlator ships GStreamer and
its plugins (release notes of several versions list "missing GStreamer
plugins" as fixed). winetricks `mf` copies Microsoft's DLLs, which cannot be
redistributed.

## 4. The change

- `build/stages/gstreamer.sh`: GStreamer's own iOS release 1.28.7
  (`gstreamer-1.28.7-xcframework.tar.xz`, sha256
  `2b1233ba3d1f8166bfa85f664709ee5ff36b81e82b9652a1d3e79c1783da9584`, equal
  to the published `.sha256sum`), its `ios-arm64` slice. winegstreamer's
  seven unix sources plus a generated plugin registration are prelinked with
  `libGStreamer.a` (`ld64 -r`, two passes so that common symbols are hidden
  too, the second with `-S`: the debug map named every archive member by its
  path on the workstation, which `verify-ipa.py` rejected) into one 47 MB object exporting `winegstreamer_unix_call_funcs` and
  `rust_eh_personality` only. Its imports resolve against
  `libntdll_unix.a` (`NtQueryInformationProcess`, `ntdll_wcstoumbs`), the SDK
  frameworks VideoToolbox, CoreMedia, CoreVideo, AVFoundation, OpenGLES,
  AssetsLibrary, Foundation, IOSurface, Metal, QuartzCore, CoreGraphics and
  UIKit, and `libiconv`, `libresolv`, `libc++` (a trial `ld64 -dylib` link
  left exactly the two ntdll symbols undefined).
- Plugins registered: coreelements, typefindfunctions, app, playback,
  videoconvertscale, audioconvert, audioresample, deinterlace, videofilter,
  autodetect, isomp4, matroska, audioparsers, videoparsersbad, applemedia,
  libav, vpx, vorbis, opus, ogg. `vtdec_hw` (VideoToolbox) registers at
  `GST_RANK_PRIMARY + 1` on iOS 17+, above `avdec_h264` (`GST_RANK_PRIMARY`).
- `patches/wine-unix` 0005: on iOS, register that set after `gst_init` with
  the registry disabled (`GST_REGISTRY_DISABLE=yes`, which gst.c reads; no
  plugin path, no cache file).
- `patches/madeira-unix` 0031: `load_builtin_unixlib` hands the table to
  `winegstreamer.dll`.
- `build/stages/wine-pe.sh`: configure sees the iOS headers, so
  `winegstreamer.dll` is built (its darwin `.so` is not shipped).
- `build/stages/stage-artifacts.py`: stages `winegstreamer`, `winedmo`,
  `mfsrcsnk`, `mfmp4srcsnk`, `msmpeg2vdec`, `msauddecmft`, `msvproc`,
  `colorcnv` and `resampledmo` (arm64ec), and links
  `libwinegstreamer_unix.a`.
- `app/tools/prefix-registry.py`: the `MFTRegister` keys of the five MFT
  DLLs. Checked against the keys `wineboot` writes with the workstation's
  own Wine 11.18 (same version as the pin) in a scratch prefix: same CLSIDs,
  categories, names, flags and type lists.

## 5. Open

- `vtdec` decodes asynchronously; winegstreamer ignores `vaapidecodebin` for
  that reason (synchronous drain/flush in `wg_transform`). If decoding
  stalls, rank `vtdec_hw`/`vtdec` below `avdec_h264` (software decoding on
  the CPU the game already saturates in play, but only during cinematics).
- Unity asks for D3D11 decoding (`MFCreateDXGIDeviceManager`); whether its
  source reader takes that path on DXMT, or falls back to system-memory
  frames, is not checked.
- Size: the dev executable grows from 46.5 MB to 80.1 MB, the IPA from
  630 MB to 690 MB (the object and the nine DLLs).
- Notices for GStreamer and the libraries it carries are not collected yet
  (docs/NOTICES.md, Gaps).

## 6. On the phone (2026-09-27)

One `pp phone lock` session: `pp ui --play app-367520 --pad`, then the pad:
Start Game, profile 2 (New Game; profile 1 is a game in progress, which
plays no prologue), both calibration screens, then no presses, a screenshot
every 2.5 s.

- The media path now runs: `winegstreamer.dll`, `mfmp4srcsnk.dll`,
  `winedmo.dll`, `msvproc.dll` load, `[unixlib] module ... (winegstreamer.dll)
  -> winegstreamer_unix_call_funcs`, and GStreamer initialises (one
  `GStreamer-Video-CRITICAL gst_video_info_from_caps: assertion
  'gst_caps_is_fixed (caps)' failed`). The player log has **no**
  `WindowsVideoMedia error` any more (it had `0xc00d36c4` before).
  `init_gstreamer_proc Failed to pin module` is logged and ignored by Wine
  (GetModuleHandleEx from a JIT-pool code address); it does not stop init.
- The prologue poem shows, then the screen is black and **the game is
  frozen**: the Metal HUD's frame graph is byte-for-byte the same in every
  screenshot from 7.5 s to 30 s.
- Cause, from `s1-host.log` and the player log: the video brings up 6 new
  Wine threads (Media Foundation's work queues); the 5th and 6th fail
  `arm64ec_thread_init` with `STATUS_NO_MEMORY`
  (`[va-profile] ml706 HOST MAP FAILED size=0x1000000 band=0x7c00000000`,
  `[va-scan] FAILED window=0x7c00000000..0x8000000000 ... maxgap=0x10000`):
  FEX's 16 GB host band has no free 16 MB-aligned 16 MB block left. By then
  51 FEX threads had initialised (their EmulatorData 64 MB apart in the
  band), and eleven 512 MB (`0x1ffff000`) reservations of threads 0024 and
  0028 hold another 5.5 GB there. A SEGV on thread 0048 (`[operand] ...
  the LOAD lost the high half`) follows. The earlier run, which loaded the
  profile 1 save (no video), started the same threads before gameplay and
  never hit the limit.
- So the video pipeline is the first thing that needs a few more threads
  than the band has room for at that point; the band budget, not
  GStreamer, stops the cinematic.

## 7. Four more layers (2026-09-27)

Each run: `pp ui --play app-367520 --pad`, Start Game, a New Game profile
(the cursor remembers the last slot; the runs used slot 4), no presses. Wine
tracing (`WINEDEBUG=+mfplat,+mfreadwrite,+dmo,+winegstreamer`,
`GST_DEBUG=2,WINE:5`) through the game's launch settings, cleared after.

1. **FEX band** (`patches/madeira-unix` 0032, IPA `27427d1b`). The steering
   valve sent Hollow Knight's main thread's 17 x 512 MB reserve-only
   arenas (8.5 GB) into the FEX host band [0x7c00000000, 0x8000000000)
   while the 0x7400000000 slot stayed clear; it now tries that slot first.
   After it: no `arm64ec_thread_init failed`, no `HOST MAP FAILED`, no SEGV;
   the 512 MB arenas land at 0x7400000000+.
2. **Shared textures** (`patches/dxmt` 0010, IPA `c866aa69`, `a6520948`).
   Unity sets `MF_SA_D3D11_SHARED_WITHOUT_MUTEX`, so every frame the video
   processor MFT allocates is a `D3D11_RESOURCE_MISC_SHARED` texture, and
   DXMT failed them all: `DeviceTexture: Failed to register mach port for
   shared texture` (an iOS app may not register a bootstrap service), then
   `source_reader_process_sample: Transform failed to process output, hr
   0x80004005` and Unity's `WindowsVideoMedia error 0x80004004 ...
   IMFSourceReader::WaitForSample`. DXMT now keeps such a texture and gives
   it an in-process handle that `OpenSharedResource` resolves to the same
   object.
3. **Shared handles on unshared textures** (same patch, IPA `…9d32f`). Unity's
   `WindowsVideoTextureOutput` asks its own 1920x1080 B8G8R8A8 render
   textures (bind 0x28, misc 0) for a shared handle and gives up on NULL
   (`Got null handle from IDXGIResource::GetSharedHandle`, 906 times in one
   run; a temporary probe confirmed misc=0 on every call). Such a texture now
   gets an in-process handle on first request.
4. **VideoToolbox** (`build/stages/gstreamer.sh`). With `vtdec_hw` decoding,
   GStreamer's `qtdemux`/`multiqueue`/`vtdechw0:src` threads all sat in
   cond-waits. `vtdec_hw`/`vtdec` are now ranked below libav, and
   `avdec_h264` decodes.

Where it stands (last run, libav decoding, all four in): no media, DXMT or
FEX error in either log; the source reader answers every `ReadSample` with a
sample (eight video, six audio); the video processor MFT produces them; Unity's
reading thread (0044) then stops calling `ReadSample`, the game keeps
rendering black at ~92 FPS, and GStreamer's queues wait for a consumer.
Unity's player log has only `WindowsVideoMedia::GpuSynchronizer: D3D11Fence
is not available, using ID3D11Query for synchronization`. The next place to
look is what that thread waits on after a frame (the `ID3D11Query` it polls,
or the `IMFDXGIBuffer`/keyed-mutex path of the frame it got); the thread
sampler does not resolve guest frames, so it needs a probe in DXMT's event
query or Wine's DXGI buffer.

## 8. The last two layers (2026-09-27)

Section 7's stall was a crash. Both runs of a probe build logged, at the
first video frame,
`_wassert (L"c - id_before <= Forward",L"src\\dxmt\\dxmt_deptrack.hpp",239)`
and `NtTerminateProcess ... exit_code=0x3`, right after Unity opened its
fourth render texture on the video device. The `Present` lines stop there,
and the CPU goes idle. The screen keeps the last (black) frame. Earlier runs
looked only for media, DXMT and FEX errors, so they missed this `msvcrt` line.

1. **Deptrack** (`patches/dxmt` 0010, reworked). Unity renders on one D3D11
   device and decodes on a second one. The in-process `OpenSharedResource`
   returned the very same texture object to the second device. Each
   allocation's `GenericAccessTracker`s record encoder ids, which each
   `ArgumentEncodingContext` counts for its own command queue. So one
   tracker held ids near 10^5 from the game's queue and ids near 10 from
   the video device's queue, and `TrackingSet::enumerate` asserted.
   Upstream's mach-port import builds a new `Texture` on the opening device.
   The local share now does the same: on another device it wraps the same
   Metal texture in a new `Texture` with its own trackers
   (`Texture::shareTo`). On the device that made it, it still hands back
   the same object. A renamable (dynamic) texture is refused on another
   device.
2. **Blue stripes** (`patches/wine-pe` 0008). With the video playing, every
   16-pixel group had a wrong blue channel in 8 pixels, while red, and
   nearly all of green, were right. `av_force_cpu_flags(0)` in msvproc (a
   temporary build) removed the stripes. The cause is Wine's own ARM64EC
   port of `libswscale/aarch64/yuv2rgb_neon.S`
   (`libs/ffmpeg/libswscale/arm64ec/yuv2rgb_neon.S`, still the same in
   Wine master on 2026-09-27). It moves the six Y + R/G/B sums to v10-v15,
   but keeps the original narrowing order. For `bgra` (msvproc's NV12 to
   ARGB32) the R2 output is v10, which overwrites B1's sum before B1 is
   narrowed. `argb`, `abgr`, `bgr24` and `gbrp` have the same fault. The
   fix narrows B1 and B2 first.

With both (IPA `87657d77`; a New Game, no presses), the prologue cinematic
plays with the right colours at the clip's 25 fps (Metal HUD 25.0 FPS, 40 ms
frame interval). The game then goes on to King's Pass with the Knight in
control. There is no assertion or `NtTerminateProcess` in `s1-host.log`.
