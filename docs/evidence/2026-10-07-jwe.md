Jurassic World Evolution (`epic-373a4372c20540aca7fdd880d27fa49a`), the Epic gate title.

## The staging gap: `gdiplus.dll` and `mlang.dll`

**IPA:** `Playport-26.5-753ebd58.ipa` (dev), sha256
`753ebd58ff9c5d80ed3de845bf66de2918fd0a10d591fdaa1448962254652e06`, built from the change
committed with this section.

Before (IPA `18ab92ce`, `20261007T135415`): `JWE.exe` maps at its base with no pool copy
(madeira-unix 0089, 0090), then `err:module:import_dll Library gdiplus.dll (which is needed
by L"C:\\Games\\JurassicWorldEvolution\\JWE.exe") not found` and `c0000135`. The arm64ec
`gdiplus.dll` was built but not staged: the arm64ec set is the reference bundle's plus
`EXTRA_PE`, and only the i386 one (the whole WoW64 set) was in `app/artifacts.tsv`.

The import tables, read with `llvm-readobj --coff-imports` from copies pulled off the phone
(`Documents/prefix/drive_c/Games/JurassicWorldEvolution/`: `JWE.exe`, `AnselSDK64.dll`,
`EOSSDK-Win64-Shipping.dll`, `GFSDK_Aftermath_Lib.x64.dll`, `crash_reporter.exe`), checked
against the staged arm64ec set: the only Wine DLL missing was `gdiplus.dll` (the rest are the
game's own DLLs and `api-ms-win-crt-*` API sets). Of `gdiplus.dll`'s own imports only
`mlang.dll` was missing (its others: shlwapi, ole32, oleaut32, user32, gdi32, ucrtbase,
kernel32, ntdll, windowscodecs). `mlang.dll` imports only staged DLLs. JWE.exe's delay-import
directory lies in its packed part and cannot be read statically. Its strings also name
`XAudio2_9.dll`, `XAudio2_8.dll` and `XAudio2_7.dll` in that order (Wwise loads the first it
finds at run time); 2.7 is staged and registered, so 2.9 and 2.8 are not added here.

The change: `gdiplus.dll` and `mlang.dll` in `EXTRA_PE["arm64ec"]`
(`build/stages/stage-artifacts.py`); `pp registry` adds mlang's COM classes and MIME
charset keys to the seed (`app/registry/`). Also in this IPA: `JitPool.swift`'s header
comment now says a pure x86-64 image gets no pool copy (0090).

JWE (`pp ui --play … --until first-frame+90 --shot`, `20261007T141627`): JIT 2.30 s, game
+2.88 s; no `import_dll` error. The ownership token is written and removed at exit as in
step 1. The packer's self-modifying writes into the image are handled (`Handled inline

crypt32, bcrypt and ncrypt. Pool head 74 MiB. It then ends `0xc0000005` 4.1 s in, before a

`rsaenh.dll` is freed and `uxtheme.dll`, of the same SizeOfImage (`0xc0000`), is mapped at
the same base. The pool's early-out for an address inside a known pool copy checks the entry
only by the `MZ` and SizeOfImage now at its base, so uxtheme reuses rsaenh's copy:
`DllMainCRTStartup` (uxtheme RVA `0x1fb7c`) runs rsaenh's bytes at that offset
(`str w0, [x19, #0x28]` in SymCrypt) and writes rsaenh's read-only header. Pool mapping
entries are tombstoned only at a process's exit (`ios_jit_reclaim_process`), not when an
image view is unmapped.

## The stale pool copy (madeira-unix 0091)

**IPA:** `Playport-26.5-10469f9b.ipa` (dev), sha256
`10469f9bb88520f63b6808f87edc1136433dc430d26058c8aa5cf60aa175c8ac`, built from the change
committed with this section (madeira-unix 0091 on top of the staging above).

0091 also checks a pool entry found by address against its pool copy's header: the PE
signature and file header, the optional header through BaseOfCode, and the section table,
within the first 0x400 bytes. A mismatch logs `[jit-pool] stale copy replaced` and copies the
image fresh; `add_mapping`'s overlap purge then drops the stale entry. Whether an unmapped
image's entry should be dropped at the unmap itself is left open: entries are still dropped
only at process exit or by that purge.

JWE on this IPA (`20261007T143517`, `--until first-frame+90`, and `20261007T151305`,
`--wait 120 --screenshot-after 20 --screenshot-after 60`):

    [jit-pool] stale copy replaced: entry pe=0x73fa9c0000+0xc0000 jit=0x10df40000 holds another image's header; copying fresh image for 0x73fa9d0000
    [jit-pool] STALE image mapping purged on add: pe=0x73fa9c0000+0xc0000 jit=0x10df40000 owner=0x0 (overlaps new image 0x73fa9c0000+0xc0000)
    [jit-pool] image 0x73fa9c0000+0xc0000 (uxtheme.dll) → pool 0x10e2b4000 …
    D 2C Load module uxtheme.dll (…): 73FA9C0000

uxtheme's DllMain now runs its own code and the c0000005 is gone. The process stays alive
(the first run for 648 s at about 30 % of a core, until the app was suspended in the
background, then to the end of the wait; pool head 70 MiB, nothing exhausted) but shows no
frame. Its only window is a 550×146 top-level window
centred on the 1564×720 screen (`[win-pos] #1 hwnd=0x1002c … vis={507,287,1057,433}`), made
right after uxtheme is loaded, the way a message box loads it. Its GDI content is not shown
(both screenshots black: the app shows only Metal swap chains), so its text is not known.
Just before it, the game makes `C:\users\playport\AppData\Local\EpicGamesLauncher` five times
(already there: `0xc0000035`). `JWE.exe`'s strings carry Frontier's launcher messages in
several languages, among them "Please make sure that the Epic launcher is installed before
starting the game." and "Please use the Epic launcher to start the game. Connection to the
Internet is required.", next to `com.epicgames.launcher://apps/` and `\EpicGamesLauncher`.
The likeliest reading: the game's check that Epic's launcher is installed fails, and it waits
on that message box. EOS is never reached, so there is no Epic sign-in state to show.
