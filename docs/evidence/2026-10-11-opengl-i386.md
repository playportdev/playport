## What changed

- **`patches/wine-unix` 0029** (opengl32). `make_opengl` writes WoW64 thunks that convert each
  parameter by its kind, and `unix_thunks.c` is regenerated from it. Regenerating the unpatched tree
  with the same Khronos registry files reproduces the committed file exactly.
  - **Pointers to the caller's memory, and client objects** (`HGLRC`, `HPBUFFERARB`, `GLsync`):
    converted through the calling i386 child's window (`wow64_ptr`). A pointer handed back (a mapped
    buffer, a created context, pbuffer or sync) goes back through it (`wow64_ptr32`). A host pointer
    outside the window is logged and the caller gets NULL.
  - **Values stay values:** `GLintptr` and `GLsizeiptr`, `HDC` and `HENHMETAFILE` handles, code
    addresses, EGL objects, and the debug callback's user data.
  - **Pointer-or-offset parameters** are converted only when the context has no buffer bound to the
    parameter's target. The binding is read with `glGetIntegerv` at the call. This covers:
    - vertex and attribute arrays: `GL_ARRAY_BUFFER_BINDING`;
    - element indices, including `glMultiDrawElements`'s arrays: `GL_ELEMENT_ARRAY_BUFFER_BINDING`;
    - indirect draws: `GL_DRAW_INDIRECT_BUFFER_BINDING`;
    - texture images, `glDrawPixels`, `glBitmap`, stipples, colour tables, filters and pixel maps:
      `GL_PIXEL_UNPACK_BUFFER_BINDING`, or `GL_PIXEL_PACK_BUFFER_BINDING` for reads (`glReadPixels`,
      `glGetTexImage`, …).
  - **`glGetPointerv` and `glGetVertexAttribPointerv`** return a client pointer through the window,
    and an offset as it is.
  - **Edited by hand in `unix_wgl.c` and `unix_private.h`:**
    - The window base comes from the calling thread's TEB pair, and `get_teb64` goes through it.
    - Returned strings, pixel formats, mapped-buffer pointers and the test for a driver mapping the
      caller can address all go through the window.
    - `zero_bits` and the debug-callback dispatcher are the calling thread's process's, not the last
      process to attach. An i386 child and its x86-64 parent share them.
    - A persistent map for a WoW64 caller is still unsupported, and is now logged as an error.
- **`patches/madeira-unix` 0116.** An i386 child's opengl32 gets opengl32's own WoW64 table
  (`opengl32_unix_call_wow64_funcs`), not the GL-absent table.
- **Host test.** `build/wow64/opengl_ptr_test.c` (run by `pp test`) compiles the patch's own
  conversion functions against a mock TEB pair and a mock context. It checks:
  - the base from the pair and `get_teb64`;
  - round trips at the window's edges;
  - rejection outside the window;
  - pointer or offset, by binding;
  - the three kinds of array;
  - identity for a thread without a TEB32.

  `build/wow64/test.py` also checks that the generated thunks convert each kind of parameter (14
  sample lines) and never convert a DC or the debug callback's values.
- **The `gl21` probe** (`tools/compat/probes/gl21.c`) now also builds for i686 (`gl21-i386.exe`).
  - Before its first frame it checks the converted paths with read-backs. Each check draws to its
    own cell and reads it back with `glReadPixels`. Buffer offsets are never 0, so an offset taken
    for a pointer, or the reverse, cannot pass by being NULL. The checks:
    - vertices from client memory and from a buffer;
    - indices from client memory and from an element buffer;
    - a generic attribute from a buffer;
    - a texture from client memory and from an unpack buffer;
    - `glReadPixels` into a pack buffer, read through `glMapBuffer`;
    - `glGetPointerv` for a pointer and for an offset.
  - `stress` mode is decision 0089's measurement. It has three phases, each drawing 20,000 vertices
    per frame:
    - "immediate": 20,000 `glVertex3f` between one `glBegin`/`glEnd`;
    - "client-array": one `glDrawArrays` from client memory;
    - "vbo": one `glDrawArrays` from a buffer object.
  - Under desktop Wine (xvfb, llvmpipe) both builds pass every check and finish stress mode. i386
    immediate takes 1.94 ms per frame (1.30 ms of draw calls); x86-64 takes 1.20 ms (0.57 ms).

  the display's 120 Hz (8.3 ms), so the frame time shows the pacing, not the GL cost.

  - 20,000 `glVertex3f` calls take 4.4 ms on i386, about 220 ns a call: an emulator exit, a WoW64
    thunk and a unix call into Mesa.

  - i386 is about 20 % slower per call.
  - One draw of the same vertices takes 0.01–0.05 ms on both machines.
- **Checks:** every run's checks passed, and every phase ends with `glGetError 0`.

## Not covered

- **Persistent buffer maps for i386** (`GL_MAP_PERSISTENT_BIT`) stay unsupported:
  - Wine needs Vulkan memory exported as an opaque fd, which KosmicKrisp does not have. The map is
    refused and now logged as an error.
  - `GL_ARB_buffer_storage` is hidden from i386 contexts for the same reason (opengl32's existing
    rule).
  - GL ≤ 3.3 titles do not need them.
- **Query results written to a query buffer** (`GL_QUERY_BUFFER`, GL 4.4): the result pointer is
  always taken as a client pointer.
- **Debug-message callbacks from an i386 game:** whether they reach the game was not exercised.
- **A real i386 OpenGL title** has not reached a frame yet. Counter-Strike (GoldSrc) is the plan's
  chunk 4.
