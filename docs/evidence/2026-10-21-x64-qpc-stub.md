# An x64 QueryPerformanceCounter stub (2026-10-21)

**Linear:** PLA-364. Host work only; the phone was offline. Dev IPA `48a13423` (wine-pe 0052, fex 0061,
madeira-unix 0204) is built and verified and has not been run on the phone.

## Why

- **The cost.** In RDR2, ntdll's `RtlQueryPerformanceCounter` takes 39–43 k x64→EC transitions a second
  ([2026-10-21-rdr2-cs-fastpath-and-heap.md](2026-10-21-rdr2-cs-fastpath-and-heap.md),
  [2026-10-20-rdr2-perf-arms.md](2026-10-20-rdr2-perf-arms.md)).
- **What the function does.** It already counts in user mode: the generic timer (`isb; mrs cntvct_el0`)
  converted at CNTFRQ, plus an offset. The offset is measured against `NtQueryPerformanceCounter` and
  resynced about once a second.
- **What costs.** Only the transition into it.

## What the switch does

With `env.MADEIRA_X64_QPC_FASTPATH=1` (off by default):

- **wine-pe 0052, the loader.** It binds an x64 module's import of `QueryPerformanceCounter` or
  `RtlQueryPerformanceCounter` to an x64 stub (0xd0 bytes) in a page made per process. That happens only
  when the import resolves to ntdll's x64 export thunk.
  - A `[x64-qpc]` line gives the page.
  - The `[x64-cs] … imports go to the x64 stubs` line counts the binding with the critical-section
    stubs.
- **wine-pe 0052, time.c.** It keeps its state in `struct qpc_state`. A resync writes the offset and
  `last_sync` under a sequence count. A thread that finds another one writing leaves the update to it and
  uses the offset already there, or its own on the first sync.
- **The stub.** It returns `ticks(count) + offset` with `RtlQueryPerformanceCounter`'s divisions,
  64-bit as in C, under three conditions:
  - the sequence count is even and unchanged across its reads (`lfence` between them; FEX makes it
    `dmb ld`);
  - there has been a sync, and it was less than a second of counts ago;
  - RDTSC's scale is known.

  Otherwise it jumps on to the export, which resyncs.
- **The count.** It is RDTSC's, shifted right. FEX's RDTSC is the timer shifted left by its TSC scale,
  6 at 24 MHz. The stub reads the scale once from CPUID 15h (EBX/EAX = 2^scale) and keeps it only when
  ECX equals CNTFRQ.
- **fex 0061.** It makes RDTSC self-synchronizing under the same switch (ISB before `mrs cntvct_el0`,
  or `CNTVCTSS_EL0`), as `RtlQueryPerformanceCounter`'s own read is. Without that, two reads in one
  thread could come out of order. It logs `FEX: rdtsc-self-sync enabled=`.
- **No floating point.** The stub uses none, so AFP on or off makes no difference to it.

## Host test

`tools/tests/test_x64_qpc_fastpath.py` takes the stub's bytes, `struct qpc_state`, `qpc_to_ticks` and
`qpc_resync` from the patch and runs them natively on this x86-64 workstation. It checks four things:

- **Exact values.** It gives 200,000 chosen states and counts, at scale 0 and at scale 6, with
  frequencies up to 2 GHz and offsets of either sign. In each the stub returns exactly
  `qpc_to_ticks(count) + offset`, without calling the export.
  - For these the RDTSC sequence is swapped for a load of the count; it is the only bytes changed.
- **Fallbacks.** It falls back on a due resync, a count before the last sync, an odd sequence count, no
  sync yet, and an unusable scale.
- **CPUID 15h.** It is checked with this host's CPUID, whose leaf is 0, so the scale is unusable. It is
  also checked with a FEX-like stand-in for the CPUID bytes: EAX 1, EBX 64 and ECX 24 give shift 6 when
  CNTFRQ is 24, 0xfe when it is 25, and "ask again" while it is 0.
- **Interleaving with the real RDTSC.** Four threads alternate stub and EC-path calls for 2.5 s, and no
  thread's values ever go backwards. The run went through four resyncs (sequence count 8).
