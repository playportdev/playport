# 2026-10-13: the ARM64EC FlushInstructionCache reaches FEX

**Linear:** [PLA-325](https://linear.app/playportdev/issue/PLA-325) (item E of the
[performance review](https://linear.app/playportdev/issue/PLA-618), PLA-79). Related: PLA-201
(the i386 half, wine-pe 0039), PLA-206 and PLA-309 (code beside writable pages).

**Changes:**

- `patches/wine-pe` 0044: the x86-64 `FlushInstructionCache` in `dlls/kernelbase/memory.c`, which
  returns TRUE without a syscall, now excludes ARM64EC. clang defines `__x86_64__` as well as
  `__arm64ec__` for an ARM64EC target (checked for both `arm64ec-w64-mingw32` and
  `arm64ec-windows`), so the built ARM64EC object had `#FlushInstructionCache` as
  `mov w0, #1; ret`. The ARM64EC branch it shadowed came with a Valve pick (wine-valve,
  `c352276d432`) and had never been built; building it showed two faults, both fixed in 0044:
  - its naked wrapper did not assemble (`Incorrect size for #FlushInstructionCache prologue: 8
    bytes of instructions in range, but .seh directives corresponding to 4 bytes`): the store of
    x1 sat inside the SEH prologue. It now follows `.seh_endprologue` (x1 is volatile);
  - the static `flush_instruction_cache`, called only from that asm, was dropped as unused
    (`-Wunused-function`), and the link failed on `#flush_instruction_cache`. It is now
    `__attribute__((used))`, as ntdll's functions called from asm are.

  The built `kernelbase.dll` now has `#FlushInstructionCache` as `stp; str x1; bl
  #flush_instruction_cache; ldr x1; ldp; ret`, and that calls `NtFlushInstructionCache`, whose
  ARM64EC wrapper calls FEX's `BTCpu64FlushInstructionCache` for the current process. The
  cross-process part (`open_cross_process_connection`) is `__aarch64__` only, which ARM64EC does
  not define, so it stays a no-op as before.
- `tools/compat/probes/childabort.c`: a `flush` phase (only when named), the `noflush` phase
  with `FlushInstructionCache` after each rewrite, in the same two layouts (`4k`,
  `rw-neighbour`).
- The aarch64 and i386 `kernelbase.dll` records changed too: only `memory.c`'s line numbers
  moved for them (and `winetest.exe`, which embeds them).

**Why the probe's `rw-neighbour` layout tells:** on x86-64 a store into a code page whose 16 KiB
host page also holds a written data page is not trapped (Wine's write-strip heal makes the whole
host page writable again; [SMC host page](2026-10-13-smc-host-page.md), PLA-309). There only the
flush can tell FEX of the change, which is also the case of a Mono game, whose SMC tracking is
off once its backpatcher is detected.

**IPAs (dev):** before, `7e95a2c083c6d74f65be5ded7df5a0b22b4ecf31ff2b90c4b74c09e5462c8948` (the one
installed, built from main without 0044); after, `a654254f81f941f46c6e8d1bdf7548824da62abbb90ffcf00073d007a1c7d99e`.
The probes were imported as `dir-childabort-325` and `dir-childabort-325-i386` (zips in Documents,

## The probe

| Check | x86-64 before (`pla325-before`) | x86-64 after (`pla325-after`) | i386 before | i386 after |
| --- | --- | --- | --- | --- |
| `flush 4k` | ok, 0 of 32,718 | ok, 0 of 29,732 | ok, 0 of 54,489 | ok, 0 of 54,222 |
| `flush rw-neighbour` | **FAIL, 980,469 of 996,036 stale** | **ok, 0 of 66,449** | ok, 0 of 92,046 | ok, 0 of 91,793 |
| `noflush 4k` | (not run) | ok, 0 of 29,110 | (not run) | ok, 0 of 55,421 |
| `noflush rw-neighbour` | (not run) | FAIL, 898,506 of 912,772 stale | (not run) | ok, 0 of 76,388 |

Before, an x86-64 program that flushed after every rewrite still ran the old code on 98 % of
calls in that layout. After, none. The x86-64 workers make about a fifteenth as many calls: each
rewrite is now an invalidation and a new translation. `noflush rw-neighbour` on x86-64 is PLA-309,
unchanged: without a flush nothing tells FEX there. i386 passes everything (wine-pe 0039, fex
0038). The x86-64 run ends `done FAIL` for that one check only.
