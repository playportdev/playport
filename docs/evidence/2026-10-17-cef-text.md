# Text in Social Club's CEF page on the phone: Tahoma in Blink's last resort (PLA-385)

**Linear:** [PLA-385](https://linear.app/playportdev/issue/PLA-385),
[PLA-370](https://linear.app/playportdev/issue/PLA-370).
**Plan:** [low-VA CEF](../plans/finished.md#own-low-address-space-cef).
Branch `dev/pla-291-rockstar-launcher`.

**Question:** The phone's Open of the Rockstar launcher (PLA-384, run `20261017T201653`) shows
Social Club's sign-in form with no text in the page. Does Blink draw it once its last-resort
font chain can reach Tahoma?

## Why Tahoma

- In that run the launcher and the second renderer rasterise glyphs through DirectWrite
  (`[dwrite-bounds]`, `[dwrite-ink] ink=YES`, `GetGlyphRunOutline`). The first renderer loads
  `dwrite.dll` and never asks it for a glyph.
- Blink's `FontCache::GetLastResortFallbackFont`
  (`third_party/blink/renderer/platform/fonts/skia/font_cache_skia.cc`) tries the generic
  family's default (Arial for sans-serif on Windows), then Sans, Arial, MS UI Gothic,
  Microsoft Sans Serif, Segoe UI, Calibri, Times New Roman and Courier New. Skia's DirectWrite
  font manager returns no typeface for a family the collection lacks.
- The phone's DirectWrite collection holds only Tahoma (PLA-374). With none of the page's
  families and none of the chain, the renderer has no primary font, and a release build skips
  the text without a log line.
- The chain is the one place every generic family ends; changing the generic defaults
  (prefs) or the per-character fallback would not cover a missing primary font. The owner
  chose the Chromium patch over shipping another font. No desktop A/B was run (owner's
  instruction): the phone is the test.
