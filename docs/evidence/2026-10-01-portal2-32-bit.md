## Existing launch failure

The retrieved logs contain three failed Portal 2 launches. The most recent
recorded attempt reports, before any game instructions run:

```text
map_fixed_area out of memory for 0x400000-0x45c000
couldn't map free area in range 0x10000-0x7fff0001, size 0x5c000
[img-map-fail] status=c0000017 size=5c000 limits=0..7fff0000
```

The address scan tried 32,761 placements below 2 GiB with no mapped Wine
views there; the first mmap failed with `ENOMEM`. The JIT pool report has
512 MiB total, 19 MiB head, 17 MiB tail and **476 MiB remaining**, with no
exhaustion. This is an address-space failure, not a need for a larger pool.
The log's earlier `runtime started` mark is the session root, not Portal 2.

## Why the obvious workarounds do not work

- The ARM64 loader requires a hard page-zero region covering the low 4 GiB.
  Apple's [load_machfile implementation](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/kern/mach_loader.c)
  explicitly returns `LOAD_BADMACHO` when this requirement is not met.
  Reducing the executable's `__PAGEZERO` is not a supported escape.
- The current PE stage builds aarch64 and ARM64EC DLL sets, and the FEX stage
  builds its ARM64EC/x86-64 module. It does not ship a complete i386/WoW64
  runtime. Changing a PE machine field or relocating only the launcher cannot
  convert its instruction set, pointer width or the engine's DLLs.
- FEX's pinned upstream has a separate `Source/Windows/WOW64` module. It sets
  `CONFIG_IS64BIT_MODE` to zero but uses guest stack addresses as native
  pointers in its syscall bridge and allocates its bridge below 2 GiB. Merely
  building that module on iOS would encounter the same address-space barrier.
- Madeira's sub-floor support (fex-port 0060 and madeira-unix 0044) is useful
  groundwork for low pointers in x86-64 code, not complete 32-bit execution.
  Its inline translation is scoped to an image window and leaves some access
  forms to fault emulation. It is not a per-process Win32 virtual address space.
- Portal 2 also needs a 32-bit Direct3D 9 path. The existing Vulkan backend's
  D3D9 DLL is ARM64EC, not a replacement for the game's i386 imports.

## Required next experiment

A genuine attempt needs a software-separated 32-bit guest address space,
backed above 4 GiB, rather than another game setting. Before targeting gameplay:

1. Establish guest-to-host translation and allocation/protection semantics;
   preserve 32-bit pointer values, wraparound, null/guard pages and per-process
   ownership. Translate instruction fetch, all loads/stores, string operations,
   atomics and code-invalidation queries, not just ordinary memory operands.
2. Port the WoW64 execution bridge, i386 ntdll/PE loading, PEB/TEB/stack setup
   and both directions of nested-pointer/callback marshalling. Native system
   calls must receive real host pointers; guest structures must retain guest
   pointers. An arbitrary high mapping alone is not sufficient.
3. Prove the loader and bridge through the product UI with isolated host tests
   for translation semantics and a Portal 2 launch that gets beyond image
   mapping. Follow the patch-series rules; do not modify upstream in place.
4. Add the 32-bit graphics/audio/input paths, then demonstrate the menu and
   actual gameplay, save/reload and regression-play Hollow Knight on the phone.

This is a new runtime capability, not an identified small title patch, and
its performance and completeness are unproven. This checkout also lacks the
recorded llvm-mingw toolchain and has no built runtime trees, so an experimental
IPA cannot currently be built or installed. No runtime change was made on the
strength of this investigation.
