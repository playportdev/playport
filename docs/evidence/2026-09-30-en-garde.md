# En Garde! plays: a data export and the Steam API's struct returns

**Date:** 2026-09-30. **Phone:** iPhone18,4, iOS 27.0, the shared reference
phone. **Branch:** `en-garde`. **Plan:** [En Garde! to its first
frame](../plans/finished.md#en-garde).
**Title:** En Garde! (Steam app 1654660), Unreal Engine 5.1.1, DXMT (Direct3D
11, feature level 11_1), SteamStub 3.1 x64 removed at launch, the Steam API
emulator in place of its `steam_api64.dll`.

**IPA** (dev): `Playport-26.5-49746c75.ipa`, sha256
`49746c7568ac9ae0f9971e52116629e4aac72008f499bba439a8c198cb3e10d9`.

## Where it stood

On `main` (IPA `48b3c99c…`) the plan's FEX fault (a null read about 20 s
in) no longer happens. Instead the game ended 1 s after start with
exit code `0xbdb2e`: an access violation reading address 4 at shipping
executable RVA `0xab72dc`, in a static initialiser the CRT runs from the entry
point (`_initterm`, table at RVA `0x5353670`):

```
call  [__imp_?xalloc@ios_base@std@@SAHXZ]
mov   rdx, [__imp_?cout@std@@3V?$basic_ostream@DU?$char_traits@D@std@@@1@A]
mov   rcx, [rdx]            ; cout's vbtable pointer: 0
movsxd rcx, dword [rcx+4]   ; faults
```

## 1. A data export resolved to the image, not the copy that runs

msvcp140 is an ARM64EC Wine builtin. Its code runs from its JIT-pool copy,
whose writable sections are its own. Its DllMain constructs `std::cout` in
that copy. But the loader resolved the game's import of `cout` to the PE
image's address (`RDX=0x71f48b4dc0`, msvcp140 `.data+0x4dc0`), which still
held the file's zeros.

**Fix:** wine-pe 0010. `find_ordinal_export` resolves an export that lies in a
writable, non-executable section of an ARM64EC module, other than ntdll, to
that module's pool copy (`xlate_ios_jit`). This is the same treatment wine-pe
0003 gives a TLS index. The run logs it as `[data-export] <image> (.data+off)
-> pool <copy>`: msvcp140's `cout`, `cerr` and the other stream objects.

The game then reached a first frame at +7.4 s, and about 1.5 s later Unreal's
crash handler ended it with exit code 3 (`Saved/Crashes/…/CrashContext`:
`EXCEPTION_ACCESS_VIOLATION reading address 0x011000010c1bb449`). Three runs
faulted at the same place with the same address, even with the executable at
different bases.

## 2. The Steam API emulator returned CSteamID the MinGW way

The fault was `mov rdx, [rbx]` at RVA `0x10bc374`, with `rbx` the function's
second argument. madeira-unix 0045 (diagnostics) prints 64 qwords of the
guest stack at such a fault. The return address it found (RVA `0x10e0910`)
names the caller:

```
mov   rcx, [rcx+0x170]      ; an ISteamUser
mov   rax, [rcx]
lea   rdx, [rsp+0x58]       ; the result's address
call  [rax+0x10]            ; ISteamUser::GetSteamID
mov   rdx, rax              ; MSVC: RAX is the result's address
```

`0x011000010c1bb449` is a Steam ID (universe 1, individual, account
`0x0c1bb449`): the value itself, not its address. An MSVC member function
returns any struct through a hidden pointer that follows `this`, and hands
that pointer back in RAX. The emulator is built with llvm-mingw, which
returns an 8-byte trivially copyable struct in RAX. Declaring the struct
non-trivial does not help: MinGW then passes the hidden pointer *before*
`this` (checked with a test object). The SDK's own MinGW form
(`STEAMWORKS_STRUCT_RETURN`) returns void, which leaves RAX undefined for an
MSVC caller.

**Fix:** gbe 0003. Every struct-returning pure virtual in `sdk/steam` goes
through `STEAMWORKS_STRUCT_RETURN` (142 declarations). Its MinGW form is now
`virtual T& f(T& ret, args…)`: `this` in RCX, the result's address in RDX
and back in RAX, which is MSVC's layout. Each implementation has that
overload: 10 are new, and the 11 void ones now return the result. The types are CSteamID,
SteamIPAddress_t and the controller and input action data.

## Not done

- **Frame rate.** 18 to 20 FPS in the first level at 720 rows, with a GPU time
  of about 48 to 58 ms per frame. The game is GPU-bound here, so it is
  playable but not smooth. Lowering the game's own quality settings was not
  tried.
- **The plan's FEX fault** (null read in ARM64EC code about 20 s in) did not
  happen on this build, and its cause was not established.
- **The release build** was not run.
- The x86 `steam_api.dll` gets the same change (MSVC's `thiscall` layout: the
  result's address is the first stack argument, returned in EAX). No 32-bit
  title was run.
