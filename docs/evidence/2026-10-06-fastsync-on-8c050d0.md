# Fastsync on Madeira 8c050d0 (decision 0054)

**Date:** 2026-10-06. **Branch:** `madeira-freeze`. **Decision:**
[0054](../decisions/0054-madeira-frozen.md). **Result:** Madeira's fastsync,
ported as Playport patches onto the frozen `8c050d0` layer, builds, passes the
gate on both cohort titles, and Portal 2's walk runs with about 10 % fewer
wineserver requests a frame than deps-latest. **Fastsync is on by default
(owner, 2026-10-06); off was not measured on this base.**

## The port

Sources: the `madeira-main` reference branch's re-ports onto wine-11.19 (its
`patches/wine-port` 0075, 0076, 0078), its evidence
(`docs/evidence/2026-10-06-madeira-bbbf8d0.md` and
`2026-10-06-portal2-madeira-wow64.md` on that branch), and Madeira's 89710fc.

| Patch | Madeira commit | Files | Where it is built |
|---|---|---|---|
| `wine-unix` 0015, the server cells | wine fork e200a5e | `server/event.c`, `semaphore.c`, `inproc_sync.c`, `object.h`, `thread.c`, `include/wine/madeira_fastsync.h` | the wineserver archive compiles these from the Wine tree (`build/stages/unix-gaps.sh` and Madeira's `build/wineserver/build.sh`); no `*_ios.c` replaces them |
| `wine-unix` 0016, the client | wine fork f6848ad | `dlls/ntdll/unix/sync.c`, `unix_private.h` | `sync.c` is compiled from the Wine tree by Madeira's `build/ntdll-unix/build.sh` |
| `wine-unix` 0017 | wine fork f674487 | `include/Makefile.in` | makedep in the unix tree's configure |
| `madeira-unix` 0081 | 89710fc | `build/ntdll-unix/server_ios.c` (`madeira_fast_flush_pid()` at process init) | the `server.c` replacement |

- 0015 applied as it is; 0016 needed a 3-way merge in `sync.c` over `wine-unix`
  0006 and 0007. The changed lines of all three are identical to madeira-main's
  patches, and the resulting `sync.c` equals madeira-main's except the
  `madeira_cfg.h` include comment.
- madeira-main's 0059 (config.h first in `sync.c`) is already `wine-unix` 0001.
- Madeira's resolver `madeira_cfg_sync_engine` (ee3d5c0) is not ported: Wine
  reads `MADEIRA_FASTSYNC` itself, and madsync stays off by `madeira-unix` 0014.
- System APCs: `wine-unix` 0002 is unchanged. On this base it already keeps
  every system APC no waiting thread takes on its own thread and never drops it,
  which is what madeira-main's rework of 0002 restored over Madeira's 074e0e3
  (not in this base). A fastsync wait that its park (at most 2 ms) does not
  satisfy reaches the server wait, where the APC runs.
- App: `Fastsync.swift` sets `MADEIRA_FASTSYNC=auto` for every session before
  the runtime starts (`0` with Settings › Developer › Fastsync off, dev builds,
  `set:dev.fastsyncOff=true`), the fastsync part of madeira-main's 534230b.
- `libntdll_unix.a` and `libwineserver.a` changed (`app/artifacts.tsv`); the
  Wine PE records did not.

The first three columns are madeira-main's table (its
`2026-10-06-portal2-madeira-wow64.md`).

- The request reduction carries over: 44.5 requests a frame in the walk,
  as madeira-main's 44.6 with fastsync on, against 49.6–49.8 without it.
- The CPU power did not: 289 mW is deps-latest's level (281–298 mW across its
  runs), not madeira-main's 248 mW. Without an off run on this base, one run
  does not separate fastsync from run-to-run spread.
- Frame rate, GPU time and hitch counts are within deps-latest's spread (its
  load segment alone spans 52–268 at ≥ 25 ms).
- **Not measured:** fastsync off on this base (the owner ruled it unneeded;
  the off run was stopped in its cool-down, before it launched), and Hollow
  Knight's `pp perf` route. A release-variant play was not run (the driver
  needs the dev app).

The dev toggle was set to off for the stopped run and set back to on
(`set:dev.fastsyncOff=false --keep-settings`) before the app was ended.
