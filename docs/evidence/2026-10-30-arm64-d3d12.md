# An ARM64 Direct3D 12 program for a native ARM64 child (2026-10-30)

**Linear:** [PLA-518](https://linear.app/playportdev/issue/PLA-518) (spec
[PLA-516](https://linear.app/playportdev/issue/PLA-516); decision
[0170](../decisions/0170-native-arm64-guests.md), proposed). Builds on PLA-512 (the native ARM64
child, [evidence](2026-10-30-native-arm64-child.md)) and PLA-513 (the aarch64 vkd3d-proton, DXVK
`dxgi` and Khronos loader under `Runtime/vulkan*/aarch64-windows`).

**Status: host side done; the phone runs have not been made.** The program was written and
checked in the side copy `.work/worktrees/bnet-runtime` (decision 0117), which may not reach the
phone. The runs below are to be made from the main checkout once the branch has moved there.

## The program

`tools/compat/probes/d3d12.c`, built by `tools/compat/probes/build.sh` with llvm-mingw 20260922:

- `d3d12/d3d12.exe`: aarch64 (Machine `0xAA64`), 89,600 B; imports `d3d12.dll`, `dxgi.dll`,
  `KERNEL32.dll`, `USER32.dll` and the C runtime's `api-ms-win-crt-*`.
- `d3d12-x86_64/d3d12-x86_64.exe`: the same source for x86-64, 93,184 B, only to check the program
  under desktop Wine.

Steps, each with its exit code on failure: a 1280x720 window (2); `CreateDXGIFactory2` and the
first adapter (3); `D3D12CreateDevice` at feature level 11_0, then the highest feature level,
shader model and binding tiers it reports (4); a direct queue and a flip-discard swap chain of two
`R8G8B8A8_UNORM` buffers from `CreateSwapChainForHwnd` (5); a root signature
(`D3D12SerializeRootSignature`), a pipeline state from Shader Model 5.0 bytecode and a vertex
buffer (6); frames for 5 seconds, or `seconds N` from the command line: clear to dark blue
(0, 51, 102), a red-green-blue triangle, `Present(1, 0)`, wait on the frame's fence (7); the last
frame's back buffer copied to a readback buffer, where pixel (4,4) must be the clear colour and
the centre pixel the triangle's (8). Exit 0 when every step passes.

The log is `<dir>\d3d12.log` (and OutputDebugString): the adapter's name, IDs and memory, the
file each of `dxgi`, `d3d12`, `d3d12core`, `vulkan-1` and `winevulkan` was loaded from, feature
level, shader model, swap chain size, time to the first present, frames and rate, the two pixels,
and `done ok` or `done FAIL at <step>`.

The shaders are `d3d12.hlsl`, compiled once to DXBC by `tools/compat/probes/d3d12-shaders.sh`
(`hlsl.c`, D3DCompile, run under desktop Wine with no display) into the committed `d3d12_dxbc.h`
(vertex shader 656 B, pixel shader 556 B), so `build.sh` needs no Wine. Running the script again
gave the same header byte for byte.

**The display.** The authorized sway session was not running. Under an owned `xvfb-run -a`
display the program reached the swap chain step and stopped there as it should: Mesa logged
`No DRI3 support detected - required for presentation`, vkd3d-proton `Surface is not supported
for presentation`, the log ended `done FAIL at swap chain`, exit code 5. The run above was made
in an owned headless sway instead (`WLR_BACKENDS=headless`, its own Wayland and IPC sockets and
Xwayland `:1`, the program on Xwayland; no physical output, stopped after the run); the owner's
niri session was not used. The workstation cannot run the aarch64 build.

**The Vulkan backend on the phone needs no change.** How the aarch64 set reaches a Local game:

- `LaunchSettings.resolve`: `graphics` is the game's choice, else the global one, else Vulkan
  (decision 0153: `GraphicsBackend.default` is `.vulkan`, and a title importing `d3d12.dll` is
  Vulkan regardless). Only a DXMT choice made in Settings or on the game's page gives DXMT.
- Vulkan sets `PLAYPORT_DLL_OVERLAY=vulkan` (`,vulkan-loader` with `khronosVulkanLoader`);
  `wine_host.c` `link_system32` → `link_wow64_farm("sysarm64", "aarch64")` links
  `Runtime/aarch64-windows` into `drive_c/windows/sysarm64` and the overlays' `aarch64-windows`
  sets over it: `Runtime/vulkan/aarch64-windows/{d3d12,d3d12core,dxgi}.dll` replace Wine's
  `d3d12`/`d3d12core` and DXMT's `dxgi`. The native child's loader takes its DLLs from
  `sysarm64` (wine-pe 0056).
- `vulkan-1.dll` in `sysarm64` is Wine's aarch64 one unless the game's Khronos Vulkan loader
  setting is on, which links `Runtime/vulkan-loader/aarch64-windows/vulkan-1.dll` (and its
  `winevulkan.json`) instead; both end in Wine's aarch64 `winevulkan`. The phone runs below try
  both.
- Nothing in `LaunchCoordinator` or `LaunchSettings` treats an ARM64 executable specially
  (PLA-512).

So no app, launch-rule or `wine_host.c` change was made; the phone runs pin `"graphics":"vulkan"`
on the title so a global DXMT choice on the phone cannot hide the path.

## Phone runs to make (main checkout)

Not run. After the branch is in the main checkout and built there (PLA-512's runs first: they
show the native child starts at all):

```sh
./pp build && ./pp install
bash tools/compat/probes/build.sh
P=$PLAYPORT_BUILD/compat/probes
./pp phone put $P/d3d12/d3d12.exe Documents/Import/d3d12/d3d12.exe
./pp ui --action import:Import/d3d12
# 1. First frame through vkd3d-proton, DXVK's dxgi, Wine's aarch64 vulkan-1, KosmicKrisp
./pp ui --settings 'dir-d3d12:{"graphics":"vulkan","arguments":"seconds 40"}' \
    --play dir-d3d12 --until first-frame+10 --shot
# 2. The same through the Khronos aarch64 loader
./pp ui --settings 'dir-d3d12:{"graphics":"vulkan","khronosVulkanLoader":true,"arguments":"seconds 40"}' \
    --play dir-d3d12 --until first-frame+10 --shot
# 3. The program's own verdict: 5 s of frames, the readback, exit 0
./pp ui --settings 'dir-d3d12:{"graphics":"vulkan"}' --play dir-d3d12 --wait 180   # expect exit=0x00000000
./pp phone pull Documents/prefix/drive_c/Games/d3d12/d3d12.log $PLAYPORT_BUILD/ui-runs/d3d12-log
# 4. Hollow Knight on the same IPA
./pp ui --play app-367520 --until first-frame+10 --shot
```
