# The JIT pool's use, running out of it, and its size (runtime risks, item 2)

**Date:** 2026-09-28. **Phone:** iPhone18,4 (11,734 MB of RAM), iOS 27.0,
unplugged (battery 29 % to 18 % over the runs). Branch `fm/pp-rr-pool` on main
`a92d722`. Two dev IPAs, each installed with `pp install --no-build` at the start of
every device-lock session (other agents installed theirs in between):

| IPA | sha256 | What it has |
| --- | --- | --- |
| `Playport-26.5-e9d9aaa8.ipa` | `e9d9aaa8750968c20be7c58ef90233c4f0aff0b796d1af0baa4c530b1f1e1447` | madeira-unix 0034, the `pool:` lines, the outcome, the sizing |
| `Playport-26.5-6e09a517.ipa` | `6e09a51749d6345a9d7bf11043fa99e0b0479506c0477782f3e249eadd15e5bc` | the same, and a launch still running 10 s after the pool ran out ends there |

The `pool:` lines of every run below are in
[timelines.txt](2026-09-28-jit-pool/timelines.txt). Head is the head's bump
cursor, the most that image copies, guest JIT blocks and child ntdll copies
have reached; tail is what FEX's code buffers reserved from the top; alias is
the anonymous-alias table's live entries, of 4096 ([ARCHITECTURE.md, "JIT pool
use"](../ARCHITECTURE.md#jit-pool-use)).

- Nothing was refused in these runs (`head_exhausted`, `tail_refused`,
  `tail_fatal`, `alias_full` all 0), and 546 to 588 MiB of the pool was never
  used.
- The head reaches most of its mark before the first frame (Hollow Knight 164
  MiB at +10 s, The Witcher 3 206 MiB before its first frame at +18.8 s); in
  Hollow Knight the rest comes with the new game's scenes.
- The tail is FEX's first 16 MiB buffer plus one 128 MiB buffer, the most it is
  granted, in both titles. It is what the room allows, not a need: with a 256
  MiB pool Hollow Knight ran with a 49 MiB tail to its first frame.
- **Mono.** Hollow Knight is Unity on Mono (`mono-2.0-bdwgc.dll`, its JIT
  hooked by FEX's Mono support). Its JIT regions are the alias entries: 61 at
  the peak, 1.5 % of the table. The Witcher 3 has no guest JIT (1 entry).
- The frame rates of the two measured runs, for the record (the pool was
  896 MiB as before this branch): Hollow Knight 84.0 fps mean, p10 61.5;
  The Witcher 3 30.7, p10 15.7.

## The pool is in the footprint

The runtime's `ml992` line, at its start, before the game:

| Pool | Footprint | Bless (JIT activation) |
| --- | --- | --- |
| 896 MiB | 931 MB | 3.09 to 3.28 s |
| 512 MiB | 553 MB | 2.54 s |
| 256 MiB | 289 MB | 2.04 s |
| 128 MiB | 163 MB | 1.93 s |

Blessing touches every page, so each MiB of pool is a MiB of the memory limit
for the whole launch. This is why the pool is now sized from the limit
([decision 0019](../decisions/0019-jit-pool-sized-from-the-limit.md)).

## Sizing from the limit

`pp ui --action set:memoryLimitSimulatedMB=3379 --action open:settings --shot-each-action --play app-367520 --until first-frame+10`:
Settings showed *Memory limit 3.3 GB*, *JIT memory 512 MB*
(shot (screenshot not published); at the real 8 GB it shows
896 MB, shot (screenshot not published)). The play logged
`title: jit pool: 512 MiB for a memory limit of 3379 MB` and reached its first
frame at +9.79 s with head 164 MiB and tail 145 MiB: FEX still got its 128 MiB
buffer, with 204 MiB of room left.

## Running out

Each run set *Simulated JIT memory* (`set:jitPoolSimulatedMB=N`) and played
Hollow Knight:

| Pool | Result line | What happened |
| --- | --- | --- |
| 128 MiB | `pool=exhausted:head exit=0xc0000135 after_s=0` | The head filled at 112 MiB and 40 image loads were refused; the process did not start. The result screen: "Hollow Knight ran out of JIT memory. Playport set aside 128 MB of JIT memory for the game, and the game's program files filled it. A higher memory limit gives it more." (shot (screenshot not published)) |
| 184 MiB (e9d9aaa8) | none: stopped at `first-frame+20` | 14 to 20 refusals: the 8 MiB image of `steam_api64.dll` (the Steam API emulator), tried 12 times, and Mono JIT blocks (anonymous RWX, 64 to 128 KiB). The game went on presenting frames. In a second run with the pad, the screen was still black 100 s after `hk-new-game` was pushed, where a full pool reaches King's Pass. FEX's code buffers were halved to 16 MiB (`exec alloc degraded 0x8000000 -> 0x1000000`), none refused. |
| 184 MiB (6e09a517) | `pool=exhausted:head still-running after_s=14` | The same refusals (12 image, 4 anonymous RWX); 10 s after the first, the launch ended on the result screen (shot (screenshot not published)) with the game still running behind it. `pp ui`: exit 1. |
| 192 MiB | none: stopped at `first-frame+20` | head 160 MiB, 14 refusals, as at 184 |
| 256 MiB | none: stopped at `first-frame+30` | head 165 MiB, tail 49 MiB, no refusal; first frame at +7.49 s |

The tail and the alias table never ran out: with a small pool the head fills
first, because the head may not grow into the tail. Their outcomes
(`pool=exhausted:tail`, `pool=exhausted:alias`) come from the same counts and
were not shown on the phone.

## Not run

- **A launcher that starts children.** No installed title starts a child:
  Hollow Knight's `UnityCrashHandler64.exe` is refused by the runtime's spawn
  gate (`[proc-gate] REFUSING spawn … (unitycrashhandler64 gate)`), The Witcher
  3 starts none, and En Garde!'s shipping executable none either (its logs of
  2026-09-27 have no `NtCreateUserProcess`). A test program cannot be staged
  into the container ([decision 0012](../decisions/0012-the-ui-is-the-only-entry-point.md)).
  A child's cost was taken from the code and the images instead: its ntdll
  copy (ntdll's whole image, 4 MiB, plus trampolines), its first FEX code
  buffer (16 MiB of tail, given back at its exit), and its executable and the
  DLLs its parent had not loaded. `children` and `children_mb` in the `pool:`
  lines will show the first title that does start one.
- **The release build** on the phone (it compiles: `pp check --variant release`).

## ntdll copies and the DWARF in the image set

`llvm-objdump -h` of this build's arm64ec `ntdll.dll` (4,456,448 bytes, as staged in the IPA): `.text` 0x7ca65 bytes
(0.5 MiB), `.data` 0x10000 (64 KiB), and 2.5 MiB of `.debug_*` sections, all
inside its 4 MiB image, which is what a child's copy takes. Across the 51
images Hollow Knight loads, the Wine PE set's `.debug_*` sections are 40.5
MiB of the 160 MiB of image copies. The decision on sharing ntdll, and this
as a follow-up, are in [0019](../decisions/0019-jit-pool-sized-from-the-limit.md).
