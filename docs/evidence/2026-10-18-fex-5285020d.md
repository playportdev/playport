## Upstream changes taken that matter here

- **b49837f** DiskCache: the data blob race. The blob was a `fextl::vector` moved into a
  `shared_ptr` after its pointer was handed out; it is now made shared first. The disk cache
  is on by default (0056), so this one is relevant.
- **4dbb046** and **3a2b1c0**: ARM64EC `CheckCall` loads `NtDllRedirectionLUTSize` as 32-bit
  (`ldr w17`) and stops at the end of the LUT (`b.hs`, not `b.hi`). Both are in our `Module.S`
  unchanged by the series.
- **aad2c96**: ARM64EC no longer hardcodes the Windows NT syscall numbers. On Wine, which is
  Playport's case, it is inert:
  - `InitSyscalls()` still takes the Wine path when ntdll exports `__wine_syscall_dispatcher`
    (our ntdll.spec has `@ extern -private __wine_syscall_dispatcher`). On that path
    `ParseWineSyscallNumbers` and the `DIRECT_SYSCALL_WRAPPER` call through the dispatcher are
    unchanged.
  - The new `SyscallTable` (512 `svc #n; ret` pairs) and `GetNTSyscallNo` are reached only when
    that export is absent, which means Windows.
  - `InitSyscalls` now returns false only on that Windows path. The series keeps the check in
    `ProcessInit`.
  - Our syscall contract is unchanged, so nothing had to be reverted.
- **b2dffb5**: DiskCache `FormatVersion` 29 → 30. Existing caches on the phone are not used.
  They would not have been anyway, because fex 0041 keys the bucket on the FEX build. The first
  launch of each title after this IPA is a cold start.
- **e3f402a**: DiskCache FileID from the ELF build-id. It applies only to Linux: it moves
  `ComputeCodeMapId` out of FEXCore into the Linux syscall layer. The Windows side keeps its own
  `ComputeCodeMapId` in `ImageTracker.cpp`, so fex 0041–0044 are unaffected.
- **679d6c7** (rpmalloc commit/decommit hooks), **6b43dac** (no hang without
  `/proc/self/maps`) and **62580ce** (stack VmData): Linux only. The FEX hooks are under
  `#ifndef _WIN32`. On Windows, rpmalloc's new trampolines default to the same `os_mcommit` and
  `os_mdecommit` as before.

### A misplaced hunk that `pp rebase` called clean (fex-port 0033)

The first build failed in `Module.cpp`: `no member named 'Size' in
'std::optional<FEXCore::ExecutableFileSectionInfo>'`.

- **Cause:** fex-port 0033 is a "clean" pick, kept as its old file. Its hunk `@@ -651,6 +678,14
  @@ public:` adds the `[iOS-xquery] MISS` block after context (`} } } #endif return Result; }`)
  that occurs twice: once at the end of `LookupExecutableFileSection` and once at the end of
  `QueryGuestExecutableRange`. aad2c96 shifted the file by about 60 lines.
- **Effect:** the cherry-pick in the rebase tree (a merge) put the hunk in the right function.
  The build's `git am -3` of the kept file applied it at an offset, in the wrong one.
  `apply --check` succeeds either way, so the range-diff (`=`) and `flags.txt` could not see it.
- **Fix:** 0033 is re-exported from its rebase-tree commit, with only new line numbers and
  index lines, through `tools/rebase.py`'s `reexport` (trailer unchanged, as for a 3-way pick).
- **Check:** the series was applied the way `build/lib.sh apply_series` does (`git am -3` onto
  the new pin, one patch at a time), and each commit's tree was compared with the rebase pick it
  stands for. All 107 FEX picks and all 20 rpmalloc picks are tree-equal. The built `run/fex`
  tree equals the rebase tip's tree (`58dd8c6d`), and its `External/rpmalloc` equals the
  rpmalloc tip's tree (`baa258cf`).
- **Patch-ids:** `patch-id` ignores line numbers, so the re-export has the same patch-id as
  before. A build area that already applied the misplaced series would keep it; this one's
  `run/fex` was removed before the second build. The main checkout's `run/fex` lacks the new
  pin, so it is cloned again.
